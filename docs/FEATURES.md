# 产品行为：人工介入与重试

> 从 README 迁入。对应 PRD 5.5 与 7.2 / F6。

## 人工介入（PRD 5.5）

讨论进行中，用户可随时插手。**介入是一等公民**，不是普通上下文：

| 动作 | 入口 | 语义 |
| --- | --- | --- |
| **插话** | 底部面板 → 插话 | 内容进入下一批次所有（或指定）模型的上下文 |
| **定向追问** | 发言卡「追问此点」 | 指定模型针对某条发言再答一轮，插为下一批次首个发言 |
| **要求对辩** | 发言卡「就此对辩」 | 两个模型就某议题点追加专项轮次，**突破 maxRounds 上限**，不计入收敛度判定 |
| **调整立场** | 底部面板 → 调立场 | 中途改某模型立场，下一轮生效；webview 通道会写进 user prompt |
| **暂停 / 继续** | 底部面板 → 暂停 | 当前批次结束后暂停，可继续 |
| **终止并出报告** | 标题栏 | 立即结束并生成部分完成报告 |

### 三条设计约束

1. **介入不被稀释**：介入内容以独立区块 `【人类参与者介入】` 注入 prompt，
   **不进 `explored`** —— 否则会被摘要器当成"已排除方向"而淡化掉。
2. **人类发言不计入共识度**：人的表态不是模型共识的组成部分。`modelUtterancesOnly()`
   在核算前过滤掉人类与缺席发言；报告中单列一章并显式说明这一点。
3. **缺席目标不静默丢弃**：定向插话/追问的目标模型若已失效，
   介入记录会被标记 `cancelled` 并写明原因，而不是悄悄消失。

介入全记录持久化在会话中，报告末尾附录的「人类介入与专项对辩」章节逐条列出，
可完整追溯"谁在什么时候干预了什么"（正文只留问题本身的综合答案，查证材料默认折叠在附录）。

## 重试已结束的议题（PRD 7.2 / F6）

标题栏「历史」进入历史页，展示**全部**会话（含中止与失败——它们最需要重试）。
每条会话显示状态、轮次、共识/分歧数、介入次数、费用、缺席模型。

### 四种重试语义

| 模式 | 保留什么 | 重跑什么 | 何时用 |
| --- | --- | --- | --- |
| **整场重跑** | 无 | 整场，从第 1 轮 | 换一批采样重来 |
| **带着上一轮结论继续** | 上一轮结论作为「已知前提」 | 整场，从第 1 轮 | 刚才那场没聊透 |
| **仅重跑缺席模型** | 已有轮次 + 已发言模型 | 仅缺席模型一轮 | 修正单点失败 |
| **就某个分歧点再辩** | 全部历史 | 专项对辩 | 深挖某条保留分歧 |

不可用的模式会置灰并说明原因（如「上一场无缺席模型」）。

### 核心约束：重试不得制造假共识

「带着上一轮结论继续」最容易出问题——直接把上一轮的结论当本轮共识，
就成了抄自己答案的假共识。因此：

1. 上一轮结论以 `【上一场讨论的已知前提】` **独立区块**注入，
   措辞明确要求「可以认可、可以反驳、也可以指出其局限，不要因为它们被列出就默认认同」；
2. 未决分歧逐条带上各方原话；**当场判不了、已搁置**的分歧单列一节并写明缺的是哪份证据
   （那是下一场最可执行的下一步），同时声明「上一场缺的证据，今天未必还缺」；
   已消解的既不进前提，也不再列为可辩对象；
3. 这些前提**不写入** `confirmed` / `open`，因此**不参与共识度核算**；
4. 有自测专门验证前提文本不伪装成「已确认共识」或「已排除方向」。

### 重试产生新会话，不覆盖原记录

原报告是决策依据，必须保留。重试会：
- 用原议题 + 原配置创建**新** `Topic`（`continue` 模式追加上一场报告摘要到背景材料）
- `dispute` 模式只让两个对辩方参与，`fill-missing` 模式只让缺席模型参与
- 在新会话上标注 `retryMode` 与 `retrySourceId`，历史页显示「重试」徽章
- 专项对辩不计入收敛度判定，报告中单列一章

### 不可执行的重试会被拒绝

`validateRetryPlan()` 在执行前拦截并给出可操作提示——
例如「上一场没有缺席模型，无需补跑。可改用『整场重跑』」，
避免用户等一个必然失败的过程。

## 数据备份与同步（GitHub 仓库）

数据只在本机，但要能换台机器接着用：设置页「备份」一栏填一个**你自己**的 GitHub 仓库
（`owner/repo` 或仓库地址），Torra 把整机数据打包成一个 `torra-backup.json` 写进该仓库 ——
一个 JSON 文件 + 仓库自带的提交历史，不需要额外的服务端。

| 项目 | 口径 |
| --- | --- |
| **收纳** | 各场会话存档与报告、适配器配置、插件落库的数据与助手会话、偏好、模型清单与插件状态（含密钥的**引用名**） |
| **不收纳** | API Key 本体（只在系统钥匙串；要带走见下面的「密钥袋」）、会话里的图片二进制、导出文件、日志、网页模型的分区登录态、`pi/` 下的明文凭据 |
| **合并** | 按文件逐份取修改时间较新的那一份；远端独有的存档会收进来，本机删掉的不会把远端抹掉 |
| **闸门** | 推送前先剔除疑似密钥字段，命中 `sk-` / `ghp_` / `github_pat_` / `"apiKey":"长值"` / Cookie 串 / `Authorization` 头就整次中止 |
| **令牌** | 细粒度 PAT（Contents 读写；首次建仓再加 Administration），只写进系统钥匙串 |
| **定时** | 可开自动备份（每小时 / 每 6 小时 / 每天），从上次同步算起；默认关 |

几个刻意的取舍：

1. **不整包覆盖**。两台机器各跑各的场次时整包覆盖会丢数据，所以按文件比时间戳逐份取新的；
   时间戳相同时本机那份胜出，保证同一份输入永远得到同一个结果。
2. **删除不传播**。这里没有「本机删掉 = 远端也删掉」这条规则 —— 会话存档是用户唯一的数据，
   一次误删、一次清目录不该反噬另一台机器上的历史。要删就得自己去仓库里删。
3. **恢复只读不写**。拉取把远端那份落到磁盘就停，不回推、不合并转发，避免顶掉别台机器刚推上去的版本。
4. **远端包读不懂就报错**。备份包结构版本比本机新时宁可让用户先升级 Torra，
   也不拿旧代码去猜新字段 —— 猜错就是把别人的存档写成半截。
5. **定时任务只让路、不打扰**。自动那一拍要同时满足「没讨论在跑」与「没有别的手动动作在进行」才动手，
   因为讨论进行中存档正在连续变化，此刻打包等于备份一份「说到一半」的现场。跑失败不弹窗，
   原因写进「上次备份」那几行与日志；并且失败不会把「上次同步时间」推前，所以补一个「等满一个周期再试」的闸门，
   免得令牌过期时按节拍把日志和远端请求刷爆。顺带拉取（双向同步）是显式选项，默认只推不拉 ——
   让定时器悄悄覆盖本机文件的风险，比「另一台机器的新场次晚一点到手」大得多。
6. **收什么按「丢了能不能长回来」划**。插件自己落库的研究主线、学者工作台的文档、助手会话，
   和会话存档一样是删了就没了的东西，所以它们进了包（结构版本因此升到 2）。
   反过来，图片二进制、日志、导出文件、网页模型的分区登录态体积大或能重来，不收。
   这条判据由黑名单先回答：`keys` / `pi` / `logs` / `chat-assets` / `exports` / `flags` 这几个顶层目录
   无论白名单将来怎么改都进不了包 —— `pi/auth.json` 是 SDK 明文写盘的一份登录凭证，
   光靠「白名单没写它」拦不住哪天顺手把整个目录加进去的人。

### 密钥袋：把 Key 也带走，但它是可选的

按上面的口径，备份包里有各条 Key 的**引用名**、没有值，换台机器恢复出来还得把每把 Key 重贴一遍。
看起来更省事的办法是把 `keys/` 里那些 `.bin` 一起打包 —— 它们是 Electron safeStorage 的密文，
Windows 上就是 DPAPI：官方口径是「通常只有拥有相同登录凭据的同一用户才能解密」，
所以密文换台机器（哪怕同一个用户名）解不开，同步过去只是一袋打不开的字节。
真要跨机器带走，只剩口令加密这一条路，于是就有了密钥袋。

开了之后，备份会额外往仓库里写**第二个文件**（默认 `torra-backup.secrets.json`，和数据包同目录、不同文件）：
口令经 scrypt 派生（N=2^15、r=8、p=1，单次约 32 MB 内存，慢到让在线试探没意义），
用 AES-256-GCM 把钥匙串里的条目整袋封起来，信封头的字段（条数、生成时间、设备名）算进认证数据，
改一个数字就整袋解不开。它和数据包语义不同：**整份覆盖、不参与按时间戳合并** ——
两条语义混在一个包里，就会出现「分享一份讨论存档时顺手把密钥也分享了」这种挽回不了的事。
备份自己的那把 GitHub 令牌（引用名 `github:backup`）永远不进袋：
袋子里装着能写这个仓库的凭据，等于把锁和钥匙钉在同一块板上寄出去。

口令的命比袋子短：它只存在于主进程内存，不写进偏好文件、不进日志、不通过 IPC 回到界面，
应用重启就没了，需要下一次备份或恢复前重新输一次。
因此界面上那三个动作各自有明确说法 —— 没口令时数据照推、远端那份袋子一个字不动；
恢复时远端有袋子而本机没口令，就只恢复数据并把这句话显示出来。
口令丢了等于钥匙丢了，Torra 这边没有任何找回途径（没有服务端、没有第二把钥匙），
远端那袋密文就此作废，只能在本机重贴 Key 后再备份一次覆盖掉它。
默认的关闭状态就是最省心的状态：只同步引用名，闸门照旧一条不少。

## 主持小结的截断抢救与重载接回

有一次真实故障：研讨跑完三轮，画布却空白，状态栏写着「主持小结中 · 0/3 已返回」，
底下那行还在走秒（首字 29s、已收 770 字）。发言一条没丢，丢的是**整场结论**。
两件事叠在一起才造成这个画面：

1. **主持的输出被端点按长度上限切在半路**。日志里两次请求都是 `stop=-`（没有 stop_reason）、
   且各自停在半个键名上，就是被 `MODERATOR_MAX_TOKENS` 硬切的形状。旧逻辑把读不通的 JSON
   一律判成「不是合法 JSON」，重打一次仍被同样截断，于是整场以 `no-moderator` 收场 ——
   共识、分歧、台账全空。现在常量抬到 8192，并且**已完整写出的那部分要抢救回来**
   （`src/shared/jsonSalvage.ts`）：数组切开后已写完的元素保住，只写了一半的嵌套对象
   整体丢弃（半个 callout 会被当成「主持真的点名了」），键名后没有值就丢这个键但不丢整条，
   半个字符串半个数字一律不猜。抢救**不放宽判据**：救回的内容照常过 `validateModeratorDigest`，
   该驳回还是驳回。驳回理由也分开了 —— 「输出被长度上限截断」会附带压缩指令
   （claim 与论据 ≤60 字、`open_disputes` ≤5 条、`summary` ≤200 字），
   而不是让模型把同一份长文原样重写一遍再被切一次。
2. **渲染层重载后追不上进行中的场次**。事件是单向推送、不重播：渲染层一旦重载
   （崩溃自愈、手动重新载入、dev 热更新），它的 store 就是空的，而主进程还握着本场已跑完的
   发言 —— 那一刻用户看到的「0/N 已返回 + 空画布」和「内容真的没了」完全分不出来。
   `session:state` 原先只回 state/round/费用几个计数，恢复入口等于没有。现在它返回整份快照，
   渲染层挂载时接一次（`adoptLiveSession`），把发言、共识、分歧、分数、介入全部重建出来，
   并提示「已重新接入进行中的讨论」。`live` 的判据是主进程的 `discussionActive`，不是
   「手里有没有编排器」：跑完的那场不会把编排器置空，state 还停在 `REPORT_GEN`
   （终态由 done 事件表达），照对象存在性判就会把「看完报告顺手刷新一下界面」误判成
   进行中场次，硬把人拽回上一场。已结束那场要看有正路 —— 历史 → 回放。

### 判死只认「有没有动静」，不认「发了多久」

`sess_mva8gp5k_1` 的画面：清言·网页 在页面里还在逐字生成、思考计数器还在跳，
研讨屏写着「本轮超时未响应 · 已跳过」。那一刻有两个独立的墙钟在判它死：

| 判据 | 旧口径 | 现在的口径 |
|---|---|---|
| 网页通道 `max_wait_s` | 从发出算起 180s | 180s **没有任何动静**才算停滞（3× 是绝对上限） |
| 编排器 `withDeadline` 硬上限 | 一次装死，`onActivity` 不顺延它 | 随活性顺延，3× 才是绝对上限 |
| 静默期（网页 150s / API 45s） | 已按活性顺延 | 不变 |

「有动静」的证据有三路：正文 / 思考 / 步骤 / 图片在增长；页面 DOM 在变
（距最后一次变化 ≤3s，覆盖「站点只把『已思考 Ns』计数器在跑」那种空窗）；
通道层有字节回来。真卡死仍由静默期先判 —— 它比这两条上限都短，
所以放宽上限不会把一场讨论陪着一个死页面耗下去。

**主持侧是同一类错，只是发生在通道层**：流式确认之后仍然用 180s 墙钟封顶，
推理模型把输出预算先花在思考上时就被当成失败掐掉，重试才通过 —— 用户看到的是
「主持总结失败重试」。现在首字节前仍是 180s（那段时间没有可观测的活性），
流式确认后换成 2× 的绝对上限，断流交给 45s 空闲闸门。

另一条独立成因：**空正文一律不重试**，把「预算被思考烧满」与「端点什么都没给」
混成一件事。前者是预算问题，翻倍上限再打一次有实质区别；后者逐字相同，
只会再烧一次钱。判据是输出用量有没有撞上本次请求的上限。

**第三种成因：封顶掐断时把已经写出来的正文整包丢掉。** 实测第 3 轮首试烧满 360s 的绝对上限，
那一刻流里已经有一份写了七成的小结，旧实现直接抛错、作废，编排器再从零重打一次（174s），
合计 534s —— 用户看到的就是「5 分多钟没结果，然后失败重试」。现在封顶掐断按「写到这里为止」
结账：正文里有 JSON 起始符就交回并标记 `truncated`，由 `parseModeratorJson` 的 salvage 分支
补闭合后照常过机械校验（校验不过照样驳回，判据一条没松）。空闲闸门不抢救 —— 那是连接真的断了，
交回半份等于把断流说成「模型写短了」，真实病因会被掩盖。

## 翻译：Index-Translate 免费公开端点

标题栏多了一屏「翻译」：贴一段原文或拖入一张图片，选目标语言，出一段译文。走的是哔哩哔哩开源的
Index-Translate 系列的**免费公开接口**（`https://index-translate.bilibili.com/v1`），
不需要 API Key，不经过任何账号登录，也不产生费用。

### 为什么不把它做成一个「讨论模型」

讨论通道那套东西要求 API Key、单价、要参与共识度核算、要记进费用台账。
Index-Translate 三样都没有 —— 端点根本不校验密钥。因此它**不进模型列表**，
而是独立一屏：讨论的账本里不该混进一笔算不出价格的调用。

### 请求口径照抄官方 `call_api.py`

提示词不是自己编的。官方本地推理服务与公开 API 用的是同一套 instTrans 提示词，
两边措辞一致模型行为才一致，所以 `src/shared/translate.ts` 里的 `buildTranslatePrompt`
逐条对齐官方 `build_prompt`：术语走【硬性要求】、自由指令走【注意】、
JSON 输入且带 JSON 约束时追加「只输出 JSON」的收尾句。

两个细节不是风格问题，是踩过坑的：

1. **必须关掉思考**（`chat_template_kwargs.enable_thinking = false`）。
   开着时 CoT 正文可能把译文整段顶掉 —— 表现是「模型说了很长一段话，就是没有译文」。
2. **术语对照写错不许拖垮整次翻译**。解析不出来的组直接忽略，
   写错的术语是笔误，不该让一次翻译失败。

### 长文按自然段分批

单次输入上限 12000 字，超了按空行切段、逐批翻译再拼接。切点选在段落边界上：
段落是最好的翻译单元，整段一坨没有空行时才退回按字符硬切。
不切的话上游会**静默截断** —— 译文少了后半截，界面却显示「翻译完成」。

### 失败要说得清

上游 5xx / 超时 / 空返回都归成一句人话（`reason`），同时把上游原文留着（`detail`）。
界面不能把失败吞成空白：那次调用到底失败在哪，得能查。

### 满屏双栏，而不是文档流卡片

顶栏只保留语言切换、交换与翻译按钮，模型和进阶约束收进设置面板；下面整块留给原文/译文。
翻译这件事本质是**对照** —— 译文压在原文下面要来回滚动，才看得出「这句译成了哪句」。
窄屏（≤860px）折成上下两栏，仍保持同一套操作。

### 图片直译与文本文件

拖入图片会以官方 `--image` 分支的多模态 `image_url` 格式发给模型，三枚模型都支持；
单图上限 12 MB。纯文本类文件直接读进原文框。端点没有文档解析能力，PDF / Word / PPT / Excel
需要用户先取出文字，界面不会假装已经读懂这些格式。

### 这一屏不做什么

- 不做译文历史与收藏（那是另一件事，不该顺手塞进来）；
- 不接本地部署的 Index-Translate 服务（官方脚本支持指向自建端点，
  但那要用户自己先跑起服务 —— 先把免费公开端点这一条做扎实）。

### 研讨模式内化翻译：英文发言直接给中文

标题栏那屏翻译是「你自己拿一段东西来翻」；研讨模式里的翻译是**另一种场景**：
模型用英文说话，人要的是读懂，于是翻译得长在阅读的位置上，而不是把人导去另一个标签页。

- **谁被翻**：只翻「主体不是中文」的模型发言。判定只看正文 —— 代码块、行内代码、链接地址与
  图片地址不参与，否则一份中文回答里夹一个函数名就会被整条送去翻译。中文发言、人工介入与
  缺席占位一律不翻。
- **什么时候翻**：发言收尾之后。流式期间不翻：半句话既判断不准，也会把同一请求打很多次。
- **翻成什么样**：忠实译，不总结、不扩写。提示词要求保留 Markdown 的段落、标题、列表与引用；
  代码、公式、URL、文件路径和模型名原样不动；专有名词首次出现时括号里保留英文。
- **在哪看**：研讨屏的发言卡与右侧「聚焦」栏共用同一份译文缓存 —— 同一句话只发一次请求。
  卡片上标一枚「译文」角标，点「看原文」随时切回模型原文。
- **失败了怎么办**：正文照旧显示原文（不吞发言），角标变「重试译文」，点一下重发。
- **账本不受影响**：译文只是阅读层。落盘、报告、引用核验、共识核算仍以模型原文为准 ——
  否则「模型说过什么」和「人读到什么」会变成两本账。

## 聊天模式：原生与提取两种视图

网页模型的一轮发言本来就是两半条链路：**把话送进去**（输入框、粘贴图片、点发送），
和**把答案读回来**（在回复容器里盯到判完）。后半条依赖站点结构，而站点天天改版。

顶栏的「原生 / 提取」开关决定这后半条走不走。**聊天模式默认原生**，研讨模式仍必须提取
（主持要拿正文做上下文，读不回来就没法往下讨论）。

| | 原生（默认） | 提取 |
| --- | --- | --- |
| 答案在哪 | 各家自己的页面上，右侧一次贴出多枚 | 读回本地，进卡片、历史、报告、可复制可导出 |
| 站点改版的影响 | 打断不了：投递那半条不碰回复容器 | 读回失败，卡片报「未捕获到内容」 |
| 会不会挂住 | 不会：投完就返回，没有 `max_wait_s` 等待 | 最长等 `max_wait_s` |
| 代价 | 本地没有正文，复制/历史/导出都拿不到 | 每站一套选择器，需要维护 |

原生模式下右侧是一面**窗格墙**：同时挂几枚不写死，由墙此刻的实际像素算 ——
每格先按地板档 420×240 划出「这一屏最多摆几格」（容量），再在不超过它的前提下挑一种摆法，
判据是「空格最少」优先、「每格形状接近 560×340」其次。所以 1920 窗口把左栏收成窄轨、
墙拖到 ~1770px 时摆得下 3×2=6 格，窄一点的窗口还是老四格，挂上墙的枚数不会比改动前少
（缝自己也要占地，见下一节）。
挤了一档要说出口，而且是两句不同的账：**下方标签条**说容量（「这一屏放得下 N 枚」），
**墙头那颗徽章**说当下的格数（「每格低于舒适档 · 6 格」）。前者只在有候补标签时存在，
后者在枚数把墙摆满、根本没有标签条的那一刻才是唯一的说法 —— 漏掉它，症状就是
「格子已经挤到读不动，界面一句话不说」。容量也不许写成摆法：三枚参与者摆成 3×1 时
说「只放得下 3 枚」，用户就以为拖宽没用，而那面墙按地板档还摆得下 12 格 ——
这句提示是他判断要不要再让墙腾地方的唯一依据。摆不下的退回下方标签，点标签换进来、
点窗格放大成独占一格；按住窗格头部拖到另一格**主体**上就把两格对调，
拖到另一格**头部**（那排标签）上就折进那一格合成一叠。墙刻意不滚动 —— 原生视图画在渲染层之上，
滚出视野的那一格会直接压在聊天区身上。

### 格与格之间的缝能拖：形状是一棵切分树

墙上每一格都能拖大拖小，而且**只影响相邻的那两格**。这条缝**自己占 7px**（一段独立的矩形），
不是 gap，也不是负 margin 借来的 3.5px：原生视图永远画在渲染层之上，
压在格子里的那几像素收不到指针。旧的 `.col-split` 那一招在它自己的布局里成立（那两侧全是 DOM），
搬到墙上就成了「看着有把手，按下去是站点页面」。

为什么是切分树而不是共享轨道的栅格：栅格里一条列轨是**整墙共用**的，拖第 1 列与第 2 列之间
那条缝，会把**所有行**的第 1、2 格一起改宽窄 —— 用户想调小的那一格，和只想保持不动的那几格
被绑在一起，这就是「只能控制一整行/一整列」的根因。切分树把每一刀记在**它自己的那个节点**上：
一个节点沿自己的轴（`x` 左右 / `y` 上下）把矩形按权重切成若干子矩形，子节点自己也可以再切。
一条缝只属于一个节点，拖动它只改该节点下相邻两个子矩形的比例（`setNodeWeights`），
子树之外的格子一像素都不动。

于是「拖动期间钉住形状」那套补丁（`hold` + `cap`）不再需要：切分树里拖动只改一个节点的权重，
形状（有几格、怎么切）压根不在被改的东西里，把手所属的格子不可能在拖动中途消失。
`layoutWall` 一次算出每格的矩形与每条缝的命中带，渲染层照着绝对定位摆出来 ——
墙是 `position: relative` 的定位上下文，格子与缝各自 `position: absolute`。

拖动的下限仍是地板档本身：`shiftSeam` 把位移夹在「这一格还剩 420（行轴 240）」上，所以拖不出破档。
这里原本另有一个更小的硬底（180px），理由是「用户执意要挤就让他挤」，而那句话在实测里变成锁死：
拖破之后墙上连一条缝都不剩，「双击恢复等分」指的是一个不存在的东西，点别的标签只是把那唯一一格顶掉
——用户的原话是「变成只能切换单个窗口无法并存了」。硬底取消，地板档就是底；要把一格占满整面墙，
走窗格头上那颗放大，那是一条说得清楚、也还得回来的路。夹位上还留了 6px（`FLOOR_GUARD_PX`）：
权重存成整数，正好夹在 420 的那一格量回来是 418，而判据一认成破档，界面就报一条用户没干过的事。

存的是**比例**而不是像素：窗口一放大，存像素那套立刻变形，而「这一格比隔壁宽一半」才是用户拖出来的东西。
存的不再是「每轴一组权重」而是**整棵形状**（`preferences.layout` 的 `wall.tree`）：
一组权重只能表达「整墙几等分、每份多宽」，所以一条缝必然牵动整行整列；
树把「哪一刀切在哪里」一起存了下来。判据只有一份（`src/shared/wall-tree.ts`），主进程、渲染层、
以及被手改过的偏好文件走同一条 —— 不合法就整份作废回到等分，不做「修修看」：
半吊子的树会画出一个谁都没拖过的形状，比回到等分更难解释。
这份值是个对象，所以主进程为它单开一条判据，且必须排在像素闸门**之前** ——
`Number({root:…})` 是 NaN，走像素那条会被判成「尺寸超出可用范围」整份拒掉，
症状是「拖得动、重启就没了」，最难查。

形状与名单对不上时（存的是三格的切法，现在挂了六枚）整份作废、回到按墙宽等分 ——
把三格的比例硬套到六格上会得到一个谁都没拖过的形状。树只记形状不记「谁是谁」：
叶子按位置重新认领 id，所以换参与者不必重建形状，拖出来的宽窄也跟着走。
（叶子同时记着「这一格叠着哪几页」—— 那不是「谁是谁」的第二份名单，
而是这一格自己的内容，见下面 Obsidian 那节。）

破档因此只剩一个来源：拖的时候墙比现在宽。拖到底之后把左栏展开、或把窗口还原，
同一组比例的每一格跟着缩，就掉到地板档以下。这时单独报一声 —— 徽章写「格子比例破了地板档」，
与「每格低于舒适档」分着说，后者是「还能看，只是挤」，前者是「比例把墙切坏了」。
两条退路都要说出来：墙头那颗「恢复等分」不依赖任何缝，整棵树一起清；
或直接点没挂上的那枚标签，它先清掉那棵树，再把这枚换进墙，容量一恢复，两格同时回到墙上。
墙上那条「未挂载」标签与下方的参与者徽章走同一段动作（`promotePane`），
因为只修一个入口时，用户就近点到的那一枚照样只会顶掉唯一那格。

双击一条缝只把**那一刀**恢复等分（其余格是用户故意拖出来的宽窄，不许被顺手抹平），
墙头那颗「恢复等分」才是整墙复位。

缝是要花钱的，格数判据从「c×地板档」变成「c×地板档 +（c−1）条缝」：950×723 的墙现在是 2×2 ——
列方向 950 本来就只够两列，行方向 3×240=720 看着够，可三行格子之间还压着两条缝，720+14=734 > 723，
第三行摆不下。省下这笔钱的写法会「说好摆得下、实际横向溢出」。

一次清两轴又牵出主进程那边的丢写：`layout:set` 是整张 layout 表的读—改—写，两个键各自拿一份
旧快照写回，后落盘的那一枚就把前一枚刚删掉的键复活了 —— 症状是「按了恢复等分，横缝还在」。
`preferences.json` 顶层那份合并救不了它，丢的是 `layout` 对象**内部**的键。所以整段读—改—写
排进同一条串行链（`withPrefsLock`），落盘写偏好的一方都从这条链上过；链上只准调裸写函数，
再套一层加锁就是自己等自己。

### 按住窗格头部拖到另一格上：起手得先把原生视图摘走

墙上想调换两枚的位置，手势只能从窗格头部起手。这一格中间那一大片不是渲染层画出来的，
是主进程贴上来的一枚 `WebContentsView`，它永远在 DOM 之上，指针一进去就归站点，
渲染层连 `pointermove` 都收不到 —— 上一条里那条缝要占住自己那 7px，是同一个原因。
所以头部那颗把手（`.wdh-grip`）是这一格唯一还听渲染层的地方，别把它当成装饰省掉。

麻烦在起手之后。用户按着的是一只把手，可他想换的是那一整格；而「松手落在哪一格」这句话
得由渲染层来量，量不到的那一片恰好就是他要拖过去的那一格。于是越过 6px 阈值的第一件事，
是把墙上**所有**视图一起摘回离屏宿主：摘的只是它挂在哪个宿主上，页面、登录态、滚动位置
一概不动，与下面那节「切进切出不重载」是同一条机制。摘完，整面墙才又是 DOM，
格子的矩形才终于认得出「这一刀落在哪一格上」。

代价是那几秒钟里看不见站点页面本身，只剩一层底色和一句话。这句话因此不能省：
每一格都写明自己此刻是什么身份（`.swap-src`「这一格正被拖着 · 拖到另一格上松手」、
`.swap-target`「松手就和这一格交换位置」，其余格是「拖到这里交换位置」），墙头同时换出
「松手：与「元宝」交换位置」。没有这一层，用户看到的就是一格突然空掉，
而那恰好是他最担心的形状 —— 页面没了。摘与贴也必须按住：贴合循环（`WebviewDock` 那个 rAF）
在让位期间由 `holdRef` 直接结束这一帧，不然就是一边摘一边每帧贴回去，屏幕上是一闪一闪。

松手那一下按格子矩形判，不按元素命中判。缝在拖动期间让开指针（`pointer-events: none`），
压在缝上、或压在墙上任何一点空隙里，都退成「包含这一点的那一格优先，其次中心最近的那一格」——
那条缝只有 7px，让它成为一种「什么都不换」的落点，手感就是拖到底却按了个空。
反过来，出了墙的界一律算取消：拖到聊天区松手不该把两格换了。三条退出路走的是同一段收尾
（Escape、窗口失焦、`pointercancel`），先把让出去的格子交还给贴合循环，再决定换不换 ——
视图回来这件事不依赖用户做对任何一步。

换的只是位置，不是尺寸：格子的宽窄属于那一格，不属于那一枚窗格，
所以两枚对调之后各自拿走对方的大小，要改大小还得回去拖缝。
一格独占整面墙时不给把手，墙上只剩一格时也不给 —— 没有第二格可换。
「谁在第几格」不再单独存 —— 切分树的叶子自带 id（`ids[0]` 是这一格露着的那页，
其余是折叠着的标签），换位置、折叠、拆出全都是改这同一棵树。
两份数据迟早会打架，打架的症状是「折起来的一叠被换人冲散」和「换了位置标签条还说老位置」。
`planPanes` 那边顺手对重复的 id 只认第一次：
同一个 id 上两次墙就是两格挂同一家站点，两个贴合循环对抢同一枚视图，症状是那一格一直在抖。
标题栏那条「已交换「A」与「B」的位置」只当回声用 —— 它住的那条一次只显示一条、新的顶旧的，
实测里常被紧随其后的登录态回执盖掉，真正的确认是墙上当下摆出来的顺序。

### Obsidian 那套手势：折成一叠、拆出来、换位置

墙不再只是「几格视图」，而是**切分树同时管几何与内容**：
叶子是「一格」，叶子里的 `ids` 是这一格叠着的那几页（第一项 = 此刻露着的那页）。
于是三件 Obsidian 里的事在同一个手势里做完了。

**落点分头与体。** 两种手势落在同一个矩形里，用户分不出意图 —— 所以按位置分：

| 拖的是 | 落在 | 结果 |
|---|---|---|
| 整格（头部把手） | 目标格**主体** | 与那一格**交换位置** |
| 整格（头部把手） | 目标格**头部** | **折进**那一格，合成一叠标签 |
| 某一页（折叠标签） | 目标格 | 把这一页**折进**那一格 |
| 某一页（折叠标签） | 墙外 | 把它**拆出去**，在原格正下方自己开一格 |

头与体分开的判据在 `hitCell` 里：它量的是目标格头部（`.webview-dock-head`）的矩形，
落在矩形内算 `head`，否则算 `body`。位置本身就说明了意图，不必再弹一个选择框。
拖到标签上就并进去、拖到空白处就自己开一格，正是 Obsidian 的手势形状。

**折叠不销毁页面。** 折成一叠之后，被折进去的那一页仍有自己的 `WebContentsView`：
登录态、滚动位置、上一场对话一概不动，只是暂时没露在墙上。
点标签条上那一张是把它 `present` 回去，不是重新加载 —— 切页改的是「这一格露着谁」，
格子本身、它的宽高、它的缝一概不动。
被折进去的标签仍可再拖走（拖去别格 = 折进别处，拖到墙外 = 拆出去自己一格），
所以「折叠」是排版，不是归档。

**折起来省出的空位要补上人。** 两页折成一格之后墙上就空出一格，
空位若不补上候补页面，用户看到的就是「我折起来一叠，另一枚却还躺在标签条里」，
省地方的意义当场没了。所以 `syncTree` 会让空出来的格子由候补页面补上，
一页都不丢（页数不变、格子数变少）。

**拖完的那一发 click 要吃掉。** 折叠标签同时挂着 `onClick`（切页）与 `onPointerDown`（起手拖），
而浏览器在 `pointerup` 之后还会补一次 click，落在标签上就等于「拖完顺手切了页」——
「把这一页折进别格」的同一下手势会在松手后又把它切成露着的那页，折叠被自己撤销。
所以拖动收尾时记下刚拖过的那一枚 id，紧跟的那一发 click 把它吃掉。

**上下拖动也只影响相邻两格。** 切分树**列优先**：先切列，每列内部再切行。
默认形状下横向与纵向拖动都只动相邻的两格，通栏的那一格一像素不动 ——
这正是「只能控制一整行或一整列」那个老问题的解法。

### 切进切出不重载：参与者整批保活

墙上摆不下的那几枚住在标签条里，此前它们既不算「用户正在看」，又常十几分钟不碰，
正好是空闲回收（10 分钟）最爱清理的形状 —— 一旦被拆，
点它换进墙时看到的就是站点重新落地那一页，上一场对话当场没了。
现在这一场的**全部网页参与者**整批报给主进程标成保活，
空闲清扫只对它们做挂起（省 CPU，不丢页面）。并行开几枚不设数量上限 ——
自动清扫只按「占了多少钱」和「多久没碰」动手，不按枚数收口。唯一还会动它们的是系统可用内存
真的低于阈值时的那一次紧急释放，而那一刻不是静默的：标签与窗格都会写明
「已回收 · 点击重新加载」，重载由用户按下那颗按钮触发。

名单是**声明式**的，先于实例存在：渲染层在参与者一变就报，而新选的那一家此刻往往
还没有实例（它是被贴上墙那一刻才建起来的）。若名单只覆盖当时在册的实例，这一报就恰好
把它漏掉，三分钟后空闲清扫拆掉它，用户点回来看到的还是重载过的页面 —— 保活白做。
所以名单单独记一份，`ensure()` 建实例时按名认领；被回收后重建的那一枚同样自动续上，
不依赖渲染层再报一次。
（已知边界：保活中的那一格若恰逢窗口尺寸变化，贴合会顺带重建实例 —— 罕见，
且那一格本来就已经空着，代价不高于用户主动点「重试打开」。）

两条链路共用同一段投递代码（含同源闸门与脚本注入），差别只在投完之后要不要接着读。
这样「切了原生就不登录、不注入、不校验来源」这类分叉不可能发生。

### 原生视图的左栏不放网页模型的卡片

回答就在右侧那一格里，左栏再复述一遍等于立第二份真相：提取来的正文会过期、会缺席、
会判完得不对，而墙上那页永远是站点自己写的。所以原生视图下网页模型的卡片**整列不渲染**，
左栏只留问题气泡与 API 模型的卡片。

隐藏按「当下的视图模式」判定，不按「这一轮当初走的哪条链路」判定 —— 切到原生，
连此前在提取模式下拿到的正文一起收起来；切回提取又全在。数据一个字没动。

卡片没了，那两张收据换地方说话：

- **投递状态**（投递中 / 已投递 / 需处理）在下方参与者徽章上，红点即「这一家没接走」；
- **重试这一轮**在当前那格窗格的头部，只在真出错时出现；
- 徽章上标「没在墙上」的模型（这一屏摆不下的那几枚）点一下换进来，重试那颗跟着出现；
  若它的实例已被系统回收，那颗标签会先变成警告色并写明「已回收 · 点击重新加载」。

站点没接走这一轮的成因是输入框失效、需要登录或被风控拦截 —— Torra 不提供任何规避验证码
或风控的手段，指向右侧那一格让用户当场手动接管。

### 原生那一屏把整屏让给网页

左栏在原生模式下只剩「复述问题」这一件事，所以它默认收成一条只有轮次编号的**窄轨**
（Q1、Q2…）：悬停用系统 tooltip 看原文，点一下就展开那一轮 —— 读全文、改问题重发、
看 API 模型的回答，都只在展开态里。顶栏那颗面板按钮是用户否决默认口径的入口，
手动选过一次之后就不再被参与者构成改回去。

两条护栏决定它什么时候不许收：

> - **有 API 参与者就不收**。网页模型的回答在墙上，API 模型的回答只有本地卡片这一份，
>   收起来等于把它唯一可见的地方藏掉；
> - **没有网页参与者就不收**。墙压根不出现，让位没有对象，收了只是白留一条空栏。

**0 轮也照收**。旧口径是「一轮都没问过时不收」，理由是窄轨上没东西可摆 —— 实测这条护栏是反的：
新会话那一整屏介绍（图标 + 一句「准备好了」 + 四枚快捷键提示）占掉近半屏，而用户此刻要看的是
右边那几格站点页面；介绍讲的「Enter 发送、Ctrl+V 贴图」在底部输入坞里本来就做得到，不必用半块屏
再讲一遍。现在左栏在 0 轮就是那条空轨，问过一轮之后逐轮长出 Q1、Q2。

输入面板同样让位：原生模式下它是横贯底部的一行细条，没聚焦、也还没打字时压成一行 22px
的单行输入框，玻璃、大阴影、20px 圆角一路降到底；一聚焦（或已经打了字、挂了附件）就长回
常态面板。焦点记在坞上而不是输入框上 —— 点附件那颗按钮会让输入框先失焦，只盯输入框的话
细条会在用户眼皮底下当场缩回去；点墙上的站点页面时焦点被原生视图接走，DOM 里不会有 blur
落进坞，那一路靠 window 失焦收尾。

这套让位能成立，靠的是骨架本身：**顶栏与输入坞住在墙够不着的那一层**
（`.cx-body` 竖排：顶栏 / 中间那一行 / 输入坞）。原生视图由主进程贴上来，永远画在渲染层
之上，压在墙矩形里的 DOM 不是「被遮住」而是根本点不到 —— 所以窄轨态下墙的下缘就停在输入条
头顶，`overlap` 实测为 0，中间那行再让出 150px 给轨道。

收起来之后墙还得把让出来的宽度真的吃下去。原先收起态只放开了 `max-width`，flex 那条仍是
`0 0 <拖出来的像素宽>`，于是 1240px 就杵在那儿一动不动，收起左栏腾出来的宽度全堆在右边，
成了一条谁也没用的死区（实测 547px，且没有任何把手拖得动它）。收起态改成
`flex: 1 1 var(--cx-web-w, 56%)` 并去掉上限：拖出来的像素宽从此只是**下限**，窗口一宽墙就跟着宽，
两格各 562px 铺满 1131px 的墙，右缘 `deadRight` 归零。展开态一个字没改，那条
`min(1240px, 100% − 400px)` 还在替轮次流守着 400px —— 让位是收起态这一侧的事，
不该顺手把展开态的护栏一起拆了。

同一处还有两个跟着窄轨走的小东西。聊天列的 `lean` 类挂在 `leanOn`（真的收起来了没有）
而不是 `lean`（该不该收起）：两者在没有网页参与者时会分开 —— 那时候墙上不出现，让位没有对象，
照 `lean` 收就把整列压成 74px，问题气泡与 API 卡片全被挤没。列宽分隔条则在收起态藏掉 ——
墙都铺满整屏了，拖它不动任何东西，留着只会让人以为右边那条死区还能被拖没。藏法是
`display: none` 而不是从组件树上摘掉：这条把手既是那 7px 命中带本身，也挂着「双击恢复默认」，
每次收起/展开都重建一遍没有道理，zoom 态那条 `.col-split` 走的也是同一扇门。


## 外部编码智能体：插拔接入

Torra 曾经打算自己做一个内嵌的 agent 助手 —— 自己写工具循环、自己写授权闸门、
自己写会话与档位。写到最后要维护的东西比预想的多：工具循环要跟每家的权限模型对表，
会话格式要自己定，模型清单要自己维护，agent 一升级就得跟着改。而外面已经有成熟的
编码智能体，它们各有各的成熟度与生态，自己再写一遍，拿到的不会更好。

于是决定改成**只说协议**：Torra 不实现 agent，只实现 agent 的**客户端**。
Agent 侧由生态里现成的适配器包承担 —— Claude Code 与 Codex 有官方的 ACP 适配器，
pi 有社区的 `pi-acp`，OpenCode 自己就带 ACP 入口。Torra 一家 shim 都不写：
给某一家写适配，等于把这一家的私有语义漏进 Torra 的通用层，四家一多就再也拆不开了。

意外的发现是：**ACP 把差异全放进了握手结果里，但差异本身比想象的大**。
协议保证的是方法名与消息形状，不保证 agent 会不会回来要授权、不保证收不收某一种
形态的 MCP，更不保证「模式」这个词在各家的意思一致。实测四家的模式分别是权限档
（Claude Code）、沙箱档（Codex）、思考档（pi），OpenCode 干脆没有模式只有配置项；
MCP over HTTP 这条路上，四家说的是四种方言（Claude Code 先发
`server/discover` 再退回老方言，Codex 说 2025-06-18，OpenCode 说 2025-11-25，
pi 压根不读建会话时给的 MCP 声明）。所以「ACP 是标准，所以接谁都行」这句话，
在协议层是对的，在产品层是空的 —— 差别只能一家一家试出来。

因此这套接入分成四层，每层只回答一个问题。

### 第零层：目录 —— 接一家新的，不用自己填

接一家新的 agent，起初是让用户自己填两样东西：启动命令与参数。填表看着最省事，
实际是最容易错的地方 —— 少一个 `--`、把 `acp` 写成 `acp serve`、或者照着某篇
博客抄了一个已经改版的命令，结果都是「连不上」。而「连不上」这三个字还什么都没说：
命令没装、没登录、协议对不上，三种的下一步完全不同。

更别扭的是第二层：用户填出来的东西，Torra 并不真知道它对不对。它只会在预检
失败时说一句「接不上」，把「你填错了」原样退回给用户 —— 而用户之所以要填，
正是因为自己不知道该填什么。

于是启动方式写进了代码里。这一层摊开的是两样来源。

**Torra 精选（十一家，离线就有）**：DeepSeek Harness、Qoder CLI 与它的国内版、
WorkBuddy CLI、Kimi Code、Gemini CLI、Qwen Code、TraeCode CLI、Copilot CLI、
Cursor Agent、Kilo Code。每一家写清三件事：怎么起、装它的那一行是什么、
有哪些已知的坑（比如 Kimi 自己那套 MCP 与 Torra 交出去的工具包不是一回事，
Qoder 的 CN 包与国际包不是同一个账号体系）。适配器包的版本照注册表里那四家的
同一套规矩钉死 —— 换了版本，兼容矩阵就要重测。

**官方目录（运行时拉，四十来家）**：ACP 生态自己维护的一份登记处，启动规格与
图标都是各家自己交的。拉回来的条目只进候选区 —— 目录不替用户决定接不接。
断网时用上一次拉到的缓存，但界面上要写明那是上次拉的：拿旧目录当新的报给用户，
比不报更坏。

本机装没装，只看一件事：**它的命令在不在 PATH 上**。这条判据看着窄，却是唯一
诚实的 —— Torra 起 agent 就是按命令名拼一条命令行，不在 PATH 上它起不来；
而装在某个 PATH 之外的角落里，用户自己敲命令能用、Torra 用不了，那不叫装了。

这里有一条不可让的规矩：**Torra 不替用户装任何东西。** 每张卡先说清本机有没有装，
没装就把装它的那一行原样给出来，复制粘贴，用户自己在终端里敲。越俎代庖的那一步
一旦替用户走了，用户就再也说不清「到底是谁装的」，出事时也说不清该卸哪一份。
确实不想装全局包的，另有「用 npx 临时跑」那个出口 —— 第一次用会把那个包装下来，
不写进用户的全局环境。

手写那条没删，但排在最后：目录收不了的那家（自家写的适配器、非公开的包）
还得有一条路能走，只是它不该是主路。

同一家的两种叫法在这里也要对上：官方目录里 Claude 叫 `claude-acp`、
WorkBuddy 叫 `codebuddy-code`，Torra 注册表里叫 `claude`、`codebuddy`。
不映射的话，用户从官方目录接一次 Claude，工作台里会同时出现两条 Claude。

图标也是各家自己交的那一枚。渲染层不放行官方那个 CDN（放行一条就等于让任何页面
都能从那儿取图），所以图标由主进程取回来、以 data URI 交给界面 ——
图就只可能是官方目录里那一张。

### 第一层：注册表 —— 有哪些家可以接，怎么起

注册表里每一条记着启动命令、适配器包与版本、登录方式、以及已知的坑。
内置四家（Claude Code / Codex / pi / OpenCode）的适配器包版本**钉死**：
适配器包跟着上游走，用户本机随时可能 `npm update` 到别的版本，而协议层通不通
取决于「这一家 + 这个版本」这个组合，不取决于「这一家」。

目录里点一下接进来的，落盘时写的也是这一份注册表，落在
`<userData>/torra/acp.json`，格式跟 Windsurf、Devin 那些工具的 registry.json 一样。
自己加的条目会盖掉内置的同 id 条目 —— 既能改内置那几家的启动方式（比如指向本机
已经装好的适配器），也能加全新的一家。加进来的条目要过一遍校验：这些字符串会被拼进
一条命令行，参数里混进 `&` 或 `|` 就能在用户机器上多跑一条命令，所以这一层不能松。
从目录里接进来的那几条同样要能删 —— 能加不能删，这条路就是个死胡同。

### 第二层：预检 —— 能不能接上，以及接不上是因为什么

「一键」的成败全在预检这一步。它起一次进程、握一次手、建一次会话、看协商结果，
然后收摊，**刻意不发 prompt** —— 预检要回答的是「能不能接上」，不是「能不能干活」。
打一次模型来验证接得上，既花钱又慢，还会让人以为已经开始了。

接不上的时候要说得清是哪一种，因为三种的下一步完全不同：命令找不到是**没装**
（或者不在 PATH 上）；起来了但要求登录是**没登录**（提示去哪登录）；起来了但协议
对不上是**对不上**。看不出是哪一种就归「接不上，原因不明」，不硬套一个更像样的话。

预检的原文里可能混着凭据 —— agent 的适配器爱把环境变量整包打出来 —— 所以贴到界面上
之前先抹一遍：键名留着（用户要知道是哪一项），值抹掉。

### 第三层：界面照着协商结果画

档位、模式、工具包挂没挂上，全都是握手结果里的东西，界面照数据渲染，
**不替各家猜含义**。这是这一层最容易出错的地方：四家都把自己的那一组叫「mode」，
按名字猜就会把设置发到错的方法上去 —— 协议把它们做成了两个方法
（`session/set_mode` 与 `session/set_config_option`），所以 Torra 记的是**来源**，
不是名字。

免掉全部授权的那一档不画。协议把它和普通模式一样列出来，但它意味着 agent 不再问
就把所有事做完 —— 主进程会拒发这类值（这是真边界），界面也不显示（这是诚实）。
agent 反过来要授权时，选项照它给的列出来，Torra 不替用户选。

### 工作台：会话、正文、改动摆在一屏

接入做通了，界面还得回答一个更实际的问题：一个能在你仓库里动手的家伙，它说的话、
它改过的文件、它停下来等你点头的那一刻，放在哪里看。第一版把这些塞进了一枚抽屉，
抽屉只有半屏宽，正文与改动只能上下叠着滚，改过的文件要另开一屏才看得见；
而外部 agent 干的活恰恰是「一边说、一边改、一边问」，三件事被拆开，因果就断了。
所以这一屏从抽屉搬成了主导航里的一个分区「编码」，形状参考 codex-host：
左边一轨放智能体与会话，中间放这一场的正文，右边按需展开改动对照。

左轨上，每一家的状态分三档：绿是整轮跑通过（握手、建会话、发一轮、打断都验过），
黄是接得上但只测到握手，灰是压根没验过。把「没量」画成「量过了」比不画更坏。
工作目录在开场前定下，开场后锁住 —— 它决定 agent 能碰哪些文件，中途换目录等于换了一场。

左轨上每一家还带着自己的官方标记 —— Claude Code 是 Anthropic 那枚放射形，Codex 是
OpenAI 的花结，pi 是它自己那三色拼出来的字，OpenCode 是官网 logo 里那枚方块。
以前画的是 Torra 自己排的首字母牌：字母牌只说明「这儿有个条目」，标记才说明
「这是谁家的智能体」，认图标比认字母快得多 —— 这一屏里内嵌助手和外部 agent 并排摆着，
用户要能一眼分清哪边是哪边。商标归各家所有，Torra 拿它只是标明这是谁的产品；
用户自己加的一家没有官方标记，就回到首字母牌 —— 不猜，也不代画。

中间的正文按「人说一句、agent 接一段」折叠：思考与工具收成一个可展开的步骤组，
正文各自成段，改过文件的那一步末尾多一张汇总卡（几个文件、+几行、−几行）。
改动本身来自协议里的 `diff` 内容块，不是从工具输出里拼出来的伪补丁：
四家的工具名、参数各不相同，`diff` 是它们唯一共同认的写法。行数也不按行首符号数，
而是按改动前后的行做多重集比对 —— 行数相同的改写会如实显示成 +1 −1，而不是 +2 −0。
右边的审查面板把每一份改动按行号对照着排，增删各染一层色。

agent 反过来要授权时，卡片上只列它自己给的选项，底下一句「选项是这一家自己给的，
Torra 不替你挑；不点就一直等着」。它没给「拒绝」时，界面补一条退路；给了就不重复。
输入坞右下角那个名字是换一家的入口，换之前会先把当前这一家送走，会话记录留在左边。
工具包挂没挂上在顶栏明说：挂上了写数量，没挂上写「未挂」，原因在悬停里 ——
那是能力差异，不是故障。

ACP 本身没有「会话记录」这个东西，但协议给了 `session/load`：让那一家把它自己留下的
历史重播一遍。这一场归谁保管、Torra 手里那份还算不算数，由这件事决定 ——
展开在后面「一份真源」那一节。Torra 这一边存的是画出来的那些行（正文、步骤、改动），
一场最多 240 行、整库最多 30 场，超出时从最旧的整场开始丢，而不是从某一场的中间截断。
会话名跟着第一句走，送出的那一刻就改，不等整轮跑完 —— 侧栏要的是「刚才那件事」。

### Torra 的工具怎么交出去

外面那几家自己会读文件、会跑命令，缺的是「Torra 这一侧」的能力：看模型清单、
跑体检、读日志、联网搜索、读写记忆库、调用应用插件。它们只认 MCP，所以 Torra 的
工具包被端成一个 MCP 服务（`src/main/acp/mcp.ts`），建会话时把地址与一枚每次会话
换新的令牌报给它们，它们自己来取。工具定义只有一份，换的是出口 —— 确认闸门、
输出上限、白名单都还在原来那层生效。

工具包挂不挂得上**不是兼容性问题**，是能力差异：只有肯收 http 形态 MCP 的 agent
才拿得到。Codex 遇到不认识的形态会直接报错；pi 这一家更特殊 —— 它声明的能力里没有
http 与 sse（`mcpCapabilities` 是 `{http:false, sse:false}`），而且把建会话时给的
`mcpServers` 整个丢掉了：声明收下了，转发给 pi 时没带上。挂不上也要让 agent 能干活，
只是它少两只手 —— 所以界面要说清为什么少，而不是让它看起来像坏了。

### 兼容矩阵：测出来的，不是承诺的

「不会有兼容性问题」这句话要有东西顶着，就是这张表。表里每一行是
「一家 + 一个版本」的实测结果，四家各测五步：握手、建会话、发一轮、打断、
会不会先问用户。

绿灯的定义很窄：握手、建会话、发一轮、打断，四样都通。工具包挂不挂得上不算进去
（那是能力差异，混进去会让矩阵显得比实际更严）。**没测过**与**测了没过**在表里
分得很清 —— 预检不花钱也不发 prompt，所以矩阵默认只到「握手与建会话」；
再往下的三步要发真的 prompt、要凭据、也花钱，跑
`npm run test:acp -- --live-full --write-matrix` 才补上。把「没量」写成「不行」
比不写更坏。

矩阵的键里带着版本号。适配器包升级了，这一格就不再作数，界面于是说「这一版还没验过」，
而不是拿旧结果糊弄。用户自己加的条目永远不绿 —— Torra 没测过它。

## 一份真源：词、身份、续聊

工作台跑起来之后有三件事一直别扭：界面上那些行是怎么来的、那一轮凭什么算「刚才那一轮」、
以及关掉之后接着聊时「这一场」究竟归谁保管。看上去是三件事，其实是同一件事的三个侧面 ——
**这一场发生过什么，只该有一份说了算的地方。**

### 第一件：Torra 自己的词

协议里各家说的话不一样：Claude Code 的工具调用、Codex 的沙箱档、pi 的思考档，
连「一轮结束」这件事的形状都不一样。渲染层要是直接认协议的消息，界面就等于把
某一家的话当成了通用话，换一家接进来得重写一遍。所以 Torra 给自己定了一套词
（`src/shared/host.ts`）：开一轮、正文来一片、工具起手、工具收尾、计划更新、收尾小结。
协议那边的话由一个投影器（`src/main/acp/host.ts`）翻成这套词，收进账本的归约只有一份
（`applyHostEvent`），主进程与渲染层共用同一份。归约要共用不是为了省代码 ——
合并规则一旦有两份，迟早有一处不一样，而不一样的那一处会被当成「界面画错了」。

意外出在重播上。读回历史时那一家送过来的事件流，跟实时那一轮形状相同，意思却不同。
实时的时候用户那一句是 Torra 自己发出去的（开轮事件里就带着它），那一家再回声一次，
界面上就会多出一句重复的话；重播的时候 Torra 手里根本没有「自己发的那一份」，
只剩回声 —— 用户那半边只能从回声里找回来。于是同一个投影器带一个「这是回放」的开关：
实时时略过回声，回放时把它当成用户那句。轮次边界也跟着变：实时时一轮是 Torra 开的，
回放时轮次由那一家给的原生标识切出来。

### 第二件：那一轮凭什么能被认回来

「能读回历史」和「读回来的历史就是刚才那一轮」是两件事，协议只管得了前一半 ——
`session/load` 存在，不代表读回来的东西能对上。所以另立一道闸门：每一轮在 agent 那边
得有一个自己的标识，Torra 读回历史时拿它对一遍，对得上才算这一轮还能被认回来。

这个标识只能取自那一家给的东西，取法也很挑：它得跨重启稳定。按位置编的号不行 ——
纯数字、`replay-1`、`turn-2`、这一场的第几个事件，每次读回来都会变，于是「对得上」
永远对不上，而这种对不上是静悄悄的：界面上看不出任何不对，只在很久以后才发现
认不回那一轮。随机 UUID 不在禁之列 —— 光看形状分不出它是持久存下来的还是每次现生成的，
分出来的是跨进程比对那一步。取键也有讲究：只认 `_meta` 里那几个带 turn 的尾键，
不按消息正文猜（正文会被用户改，键名不会）。

闸门的结果不是一个「支持/不支持」，而是三档：**能接着聊**（历史读得回来，
而且轮次标识跨重启对得上）、**能看历史**（读得回来，但对不对得上没验过）、
**不留历史**（那一家压根不给）。没验过的那一档不能写成「行」——
这正是兼容矩阵那一格的作用：矩阵量的是「这一家 + 这一版」，
`judgeResume` 把协商结果与量出来的结论合成这三档，顶栏上挂一枚小标签。
用户自己加的条目永远没有量过的结论，于是永远停在「没验过」那一档。

跨重启这件事在一次运行里根本验不出来 —— 只能另起一个进程读回来再比。
所以离线回归里那家固定装置现在自己留历史（写到文件里）、发不透明的轮次标识、
重播时把同一个标识再发一遍，「关掉进程、换一个进程、接着聊」这条路不花钱也能走通。

### 第三件：这一场归谁保管

Torra 之前在渲染层留了完整的一份正文。理由是 ACP 没有会话记录，子进程一退，
那一场就只剩这一份。留着两份的坏处很实在：两份迟早不一样，而不一样的那一份会被当成真的 ——
它就在 Torra 自己的存储里，看起来比别处权威。所以现在反过来：那一家的历史读得回来的时候，
Torra 立刻把自己那份正文删掉，只留一份索引（谁、哪一场、什么时候、那一家给的会话号）。
归档那一屏于是明说「这一场的正文在那一家自己那儿，Torra 这边只留了一份索引」，
入口从「翻旧账」变成「在那一家上接着聊」。读不回来的那一家才留兜底 ——
兜底就是兜底，界面上说清它是什么，不冒充历史。

这里有个坑值得留着：界面每来一片文字就攒一次再落盘，而「读完历史就删掉本地那份」
这个动作刚做完不到半秒，攒稿的定时器又到了 —— 它把正文原样写回去，第二份真源就这样
悄悄复活。所以「这份正文归那一家管」得跟着这一场一起活着，落盘那一刻先看这个标记。
这不是洁癖：两份一旦分叉，被当成真的会是错的那一份。

## 技能目录的分类标签：记在 Torra 这一侧

技能导入到十几条以后，那一墙卡片就只剩一排名字。想找「哪条是管科研的」，
只能挨个点进去看说明 —— 分类这件事界面没管，全靠用户的记性。

标签往哪儿存，是这一节真正要想清楚的地方，因为它看着像技术问题，其实是归属问题。
技能目录里过半条目不是 Torra 自己的东西，是指向 `~/.agents/skills`、`.claude/skills`
这些**别人家目录**的链接。往技能的 SKILL.md 里加一个 `tags:` 字段，等于替用户改别人的文件：
对方应用一更新就把它冲掉，严格的校验器还可能把未知字段报成错误，而用户根本不知道是谁动的。
「这条技能算科研还是研发」是 Torra 怎么看它，不是它自己的属性 —— 就该落在 Torra 这一侧。
于是有一份本机记录（`<数据目录>/skill-tags.json`），技能文件一个字都不动。

键用「技能目录里的那个条目名」。技能名会撞（不同应用可以同名），绝对路径会随导入方式变
（软链接和复制副本的 path 不一样），只有目录里那个名字在「断开 → 重新导入」之后还是同一个。
断开时也不删标签：移除多半是「暂时不用」，过两周重新接上时分类还在，比从头打过要像话。
读不出来就当作没有 —— 这是一份让卡片墙好找的辅助记录，一次手滑把 JSON 改坏，
不该让整个技能目录读不出来。

界面上只有两条规矩。筛选条是从**真正被用到的标签**里长出来的，按条数排：没人用过的词不上条，
一排按下去多半没反应的死键比没有条更吵。点法是「命中任意一个就留下」而不是「同时带这几个」——
想比对两堆东西时，交集筛法会在你最想看的那一瞬间给出空墙，而对着空墙没人猜得到是自己筛错了。
筛到一条不剩时界面自己退回全部，并把原因写在原来那句计数的位置上。

写之前先清洗：去首尾空白、合并重复（不分大小写）、单个截到 32 字、一条最多 8 个 ——
口径与记忆库那侧一致，别处已经定过的数不再另定一套。装不下的那几个不闷声丢，
退回界面说是哪几个没进去。落盘走临时文件加改名，跟本机其它台账一个写法。

## 会话工作树：光从谁那儿出发，落到哪一步

编码工作台原来只有一条往下滚的正文。看得出说了什么，看不出这一轮分成了几支、
哪一支刚收口、改动是从哪一步来的。于是右栏多了一棵树。

树上的节点全部由账本推出来：会话是根，轮挂在下面，步骤挂在轮下面，
带改动的轮另外长出一个交付节点 —— 一句结论，加几张能点开的文件卡。
不另存一份树：两份真源迟早分叉，而分叉之后被当成事实的往往是旧的那一份，
用户看到的就不再是 agent 真正做过的事。

**连接只认三种标识**：会话 id、轮号、步骤号。这是这一节最不肯让步的一条。
按「最近出现的那个节点」连、按坐标离得近来连，写起来只要两行，看起来很顺，
而在并行分支上它一定是错的 —— 光会飞到别人家那一步上，界面照样笑得很好看，
没有任何东西会报错。所以每条边都是显式写出来的父子关系，测试里也有一条专门断言
每条边的两端都能在节点表里找到。

**什么时候才往回连**：只有真的完成了才写「合流」。跑着的、失败的都不写 ——
画一条回连线等于替它宣称交付过了。失败的那一步标成失败，同样不往回连。

**光什么时候该出现**。只在新的一轮、新的一步、交付、完成收口这四件事上。
所以界面比的是「前后两份节点表的差」，而不是「账本有没有变」：重新推一遍树
（窗口重渲染、切一下视图）差是空的，不该再放一遍光；切会话、读回历史时，
那一屏是把旧账本重新摆出来，也不是刚刚发生，同样不放。这两件事分开，是靠一个
「这一批是整体换上的」标记来管的 —— 新节点和「新事件」看着是一回事，其实不是。

**飞行本身**。光束从顶栏那家的标记出发（新的一轮），或者从那一轮的气泡出发
（新的一步、交付），落到工作树上那个节点。颜色跟这一场一致。默认 1.2 秒，
慢起、加速、慢落。路径的弯度由事件 id 定种子：同一件事重放走同一条弧，
换一件事才换一条新的 —— 每次都不一样是设计，逐帧都不一样是抖动，
抖动的光看起来像信号不好。落地之后在节点上补一下高亮，再收掉。

**该省的都省**。空闲时停掉帧循环，页面藏起来就冻结（回来时接着飞，不一次画完），
组件卸载时把节点、监听、定时器全拆掉。尊重 `prefers-reduced-motion`：
那种设置下不飞行，只画一条静止的线并把落点点亮一下 —— 动了就是没尊重。
每一帧只改 SVG 的属性和 transform，不经过 React：走 state 的话，1.2 秒里
要重渲七十多次整棵树，最后看起来像卡了。也不用大面积模糊去模拟光晕，
一条描边加一个小点就够了；糊成一团之后，反而看不出它从哪儿来、到哪儿去。

**别忘了用户正在看的东西**。新节点出现时先把它滚到眼前，再发射 —— 否则光会
消失在某个看不见的地方。但只滚工作树那一栏，中间的聊天记录一概不动：
替用户滚走正在读的那一段，比不跟随更烦人。「跟随」可以关掉，关掉之后
只回答「在不在眼前」，不去挪人家的滚动位置。

**两处「亮起来」要分开**。正在跑的步骤和那一轮的气泡有一道细窄的同色流动边框，
完成即摘；键盘焦点走 `:focus-visible`，是另一套样式。共用一条规则的话，
用户就分不清「是我选中了它」还是「它正在干活」，鼠标点一下也会被误读成运行状态。

**树怎么摆**。缩进式竖向树：深度往右缩进，兄弟往下排。早先试过「同一层横着铺开」，
三个兄弟就把行宽撑到三张卡，而右栏只有三百来像素 —— 于是每几步就要横向滚一次，
滚完连会话根都被推出左边界，只剩半截标签。改成竖排之后，深度最多四层、
每层只缩进一格，一张卡宽就够；横向滚动留给「多会话」，纵向滚动留给「历史长」。
「聚焦」只摆当前这一场，「全部」把所有根会话横着排，合并保留全部来源连线。

**交付不塞进大气泡**。日志、命令、分支内部的提示词照旧折在步骤里，
交付只留一句短的结论和那几张文件卡。结论取那一轮最后一段正文的第一句；
没有正文就照实写「没有留下结论」，不拿命令输出凑一句。

**演示数据要自己说是演示**。真实的 ACP 一场只挂一家，Torra 今天也还没有子 agent
的嵌套事件，所以「孙分支」「并行会话」这两档在真数据里造不出来 —— 可它们正是这棵树
最容易画错的地方。因此有一份标了 demo 的演示树，藏在面板上一个「演示」开关后面，
打开时面板顶部明写「演示数据」、每张卡也带「演示」。演示冒充真跑过，比没有演示更坏。

## 换骨：把第三方 ESM 从主进程里请出去

给外部 agent 做客户端这件事，第一步就撞上一个与协议无关的麻烦：Torra 的主进程是
CommonJS 的，而 agent 生态里的包大量是 ESM。Torra 自带的助手先撞上了 —— 它把工具层
交给 pi 的 SDK，而 pi 的 SDK 是 ESM。TypeScript 把 `await import()` 降级成 `require()`，
于是启动时直接 ERR_REQUIRE_ESM。这不是抽象的风险，是这台机器上真的发生过的事：
pi 的 SDK 为了修 undici 在 Node 20.18 上的一个 bug 去改 `workerThreads` 的
`markAsUncloneable`，补丁跟着整条 import 链进了主进程。真正让人不安的不是这一个包
坏了，而是**它坏在启动路径上** —— agent 生态的发版是别人的节奏，Torra 不知道哪天
一次 `npm update` 就把一个 ESM 依赖换到了主进程的必经之路上，而症状是整个应用开不了机，
不是那个功能不能用。所以这一层的目标不是「让 pi 能跑」，是**让主进程不再装载任何
第三方 ESM**。

第二个意外来自参数说明这一层。原来的工具参数是 TypeBox 写的，看上去是工具链的硬性
依赖：类型是 TypeBox 的类型、必填是 TypeBox 算的、校验也在 TypeBox 里。量下来
不是。TypeBox 1.3.7 生成的本来就是**普通 JSON** —— `Type.Optional` 不带任何 symbol，
`required` 是在 `Type.Object` 内部算好的，`JSON.stringify` 出来就是一份标准 JSON
Schema。pi 那边 `defineTool` 是个恒等函数，运行时什么都不做。更要紧的是 pi 的参数
校验有一条显式的 JSON-Schema 分支：schema 上没有 TypeBox 的 kind 标记时，它先走
`coerceWithJsonSchema` 再交给 typebox/schema 的 `Compile` —— 必填、类型、枚举照样
拦得住，字符串与数字之间的强转也照样发生。

于是决定下来：参数说明改用 Torra 自己的一份契约（`src/shared/tool.ts`），内容就是
一份干净的 JSON Schema，`Type.*` 这套构造器照着实际用到的形状逐个对齐 TypeBox 1.3.7
的输出，连字段顺序都一样（`type, required, properties, additionalProperties, description`），
所以发给模型、发给 MCP 的东西一个字没变；传输层则自己手写（`src/main/acp/jsonrpc.ts`，
NDJSON 上的 JSON-RPC 2.0）。这条边界不能靠自觉，所以有一条测试盯着：它从
`src/main/acp/index.ts` 出发把整条 import 闭包走一遍，凡是第三方包都必须带 `require`
条件 —— 进不了 cjs 入口的包不许上这条路径。`@modelcontextprotocol/server` 留得住，
因为它发了 cjs 产物；pi 的 SDK 留不住，因为它是纯 ESM。

换骨换掉的是「装载方式」，没换掉「内置助手还在」这件事，这个差别得说清楚。
Torra 自带的那个助手今天仍然在进程内跑 pi，仍然靠那份 ESM 装载器起来。原因不是
忘了，是 ACP 这条路还缺几样东西：读回历史这一样现在有了（`session/load` 能用，
跨重启对不对得上由上面那道闸门量），但它没有「steer」（插一句话纠偏），
而 pi 的适配器又把 MCP 声明整个丢掉了。
如果现在把内置助手整个搬到 pi-acp 上，Torra 的工具包（看模型清单、跑体检、读日志、
联网搜索、读写记忆库、调用应用插件）会跟着一起消失。卡住的是适配器版本，不是 pi
本身：pi 1.4.0 两种 MCP 形态都支持，stdio 写在 `<agentDir>/mcp.json`，http 写在
`<cwd>/.pi/mcp.json`（要信任项目）。所以下一步的顺序是明确的 —— 先给 pi 一条拿到
工具包的路（换一版 pi-acp，或者把 Torra 的 MCP 服务注册进 pi 自己的配置），再把
会话与档位在 ACP 上重建，最后才轮到删旧路。在那之前两个助手并存，是诚实的状态，
不是收尾。

换骨顺手把另一件事变简单了：工具定义从此只有一份。内置助手和 ACP 的 MCP 服务读的是
同一批定义（`src/main/assistant/tools.ts`），换的是出口 —— 确认闸门、输出上限、
白名单都还在原来那层生效，而外部 agent 拿到的是标准 MCP 工具调用，模型看到的那份
参数说明不必再经过任何一层 Torra 私有的中间格式。

## 报告只有一套版式：屏幕上读的那份，与带走的那份

应用里的报告页（`ReportViewer`，主界面与历史页共用同一个）和导出的成稿 HTML 是同一套骨架：
结论在前、判断按成色分档、决定写清前提与代价、台账与账目折进末尾附录。
**导出不是把屏幕截下来**：主进程（`src/main/report/report-html.ts`）拿同一份报告对象
重排一张纸 —— 折叠、追问、导出按钮在纸上没有意义，纸只留读的顺序。

| 导出 | 是什么 | 给谁 |
| --- | --- | --- |
| HTML | 主进程重排的纸面文档（单文件、无脚本、无外链字体） | 带走、转发、打印 |
| PDF | 同一份纸面的 A4 分页 | 打印、放进文档 |
| 图片 | 屏幕上那份原样截图 | 粘进聊天 |
| MD | 纯文本结论 | 再加工 |

为什么纸要单独排一遍：屏幕上的报告有深色主题、折叠与按钮，存成文件读者拿到的是一张界面截图；
而「适合打印」是硬要求 —— 附录在文件里是展开的，`<details>` 的折叠态在打印时会被整个裁掉。
正文只展开 6 条判断、每条 2 段原文（`LEAD_CLAIMS` / `EVIDENCE_PER_CLAIM`），
判断清单与全部原文在附录里仍是全的。

几处刻意的取舍：

- **模型写的文字一律转义后进标记。** 报告正文不是可信 HTML：题目或判断里带
  `<img src=x onerror=…>` 也必须原样显示，不能进标记。
- **摘要开头那句「围绕「整道题」的……」不再复读一遍。** 题目已经印在封面，
  正文里那句只占一行的位置。只在引号段位于句首时动手，且按字面匹配整题 ——
  题目被改写过就一行都不动，宁可重复也不去猜原文。
- **没有终局审校时显式写明**「本场没有终局审校：这份报告由旧版本生成，或本场中止／
  无主持降级」，与界面同一条口径 —— 缺一层不是「这节省略」，缺一层要能被看出来。
- 长摘要按句读切段，单段超过约 160 字才切；只认全角句末标点，不碰英文句点，
  免得切碎 DOI 与小数。

自测：`npm run test:report-html`（十条：转义、缺终局审校、缺席轮号、离线承诺、
去复读、切段、附录展开）。

## 报告页里的模型、图标与图表

报告里每一处「某某说」都靠名字认人，但读者翻开时并不记得这一场请了哪几家。
所以模型身份不只以文字出现，而是先有一张图标：

| 位置 | 长什么样 | 为什么在那儿 |
| --- | --- | --- |
| 本场阵容（hero 下） | 头像 + 名字 + 通道徽标；缺席的标红，主持戴冠 | 后面读到任何名字都有对照物；缺席会少一份独立视角，要点名 |
| 逐条判断的「认同」 | 认同者的头像横排 | 「谁认同」比「几家认同」更重要，点名要点到人 |
| 保留分歧的两侧 | 头像 + 名字 | 分歧是两方之间的，不是两段文字之间的 |
| 印证矩阵 | 行 = 模型，列 = 判断，实心 = 这家认同了这一条 | 横着扫一遍才知道有没有谁一直在旁边点头却没落过笔 |
| 参与度 / 互评名次表 | 头像 + 名字 | 表格里第一列是身份，不是编号 |
| 口径与设置 | 参与模型整排 + 主持（戴冠） | 存档多年后回头查，这一场请了谁得一眼看清 |

图标取的是 `ModelAvatar`：自定义图标 → 品牌 favicon（逐源回退）→ 字母牌。
字母牌不是「图没加载出来」，是这套视觉里本来就有的兜底层 —— 报告里只存了
id 与显示名，品牌信息来自会话的模型清单，清单里没有就画牌子。

其它图标沿用同一套语言：每章标题一枚、KPI 磁贴一枚、判断的四条口径各一枚、
审校三列（前提 / 代价 / 动作）各一枚、证据折叠条一枚。
`prefers-reduced-motion` 与深色主题都跟着 token 走，没有第二套配色。

## 研讨屏的动效：只动「正在发生」的那几处

一场研讨跑起来，屏幕上真正在变的只有三件事：谁在写、写到哪儿、这一轮怎么走。
动效只贴这三件事，其余地方保持静止 —— 静止不是没做，是让「有变化」有对比。

| 时刻 | 动效 | 为什么 |
| --- | --- | --- |
| 换轮 | 画布上扫过一道带亮边的竖带（940ms，一次） | 数据不会自己冒出来，这一轮是刚开始的 |
| 发言批次 → 主持小结 | 阶段格换字时从左侧落下 | 一轮的节拍就落在这一格上 |
| 主持在写 | 状态行上边线跑一道扫描光；字数每涨一次弹一下；尾巴左侧淡入 | 二十到四十秒里，这是「没卡死」的唯一证据 |
| 一条发言在生成 | 右栏发言末尾一枚闪动光标（跟随卡上原本就有） | 光标是「还在长」的通用语言 |
| 台账新增一条 | 条目错峰落定（每条 +55ms），左侧色条先亮后归位 | 新记下的一条该被看见，而不是混进九条里 |
| 轮次条 | 分数宽度过渡 0.55s；当前那一轮里有液体在走 | 分数是逐轮落定的，宽度该跟着长过去 |
| 聚焦换人 | 标题下划一道铜线 | 读者知道这一格刚被换过，不是自己看漏了 |
| 收束 | 收尾块落下 | 这块只出现一次 |

几条红线：

- **只动 `transform` / `opacity`，不动布局** —— 图上每一个像素都参与节点命中，
  重排就是整张图在鼠标底下挪。
- **`prefers-reduced-motion` 下循环动画直接停、入场延迟归零。** 延迟不会被全局那条
  时长规则压掉，所以在全局规则里显式补了 `animation-delay: 0s` —— 否则降级之后
  条目还是会「晚半秒才出现」。
- 样式分两处：中栏与台账在 `styles.css` 的 `te-` / `cs-` 层，右栏在 `roundband.css`
  的 `rb-` 层；颜色全部走 token，明暗两套自动跟，不写死色值。
- 新增的类名都在组件里真用着 —— `test:css-dead-rules` 会扫 `styles.css`，
  写了没人消费的选择器过不了。

## 仪式感：四拍，别的都静止

「有仪式感」不是到处加动画，是**几个真正有分量的时候有形状**。全应用只留四拍：

| 拍 | 什么时候 | 看见什么 | 为什么只有它 |
| --- | --- | --- | --- |
| 开场 | 应用第一次落墨 | 整个壳 420ms 淡入 | 打开一个应用不是「白屏然后全都在」 |
| 移席 | 换一屏 | 内容列浮起 6px 落定，260ms | 读者要知道「换了一块」，而不是内容凭空替换 |
| 开议 | 从配置页进入议事厅 | 一块幕盖住议事厅约 1.2s：策略 · 开议、议题、一道铜线、几家落座的头像逐个到位，然后揭开 | 这是产品里唯一一次「开始」。幕后面第一轮已经在跑 —— 揭开时看到的是「正在说话」，不是空厅 |
| 落纸 | 报告生成 | 收尾条先落定 420ms，报告再像一页纸被放上桌（16px 上移 + 0.986 缩放 + 沿上沿扫一道铜线） | 「收束」和「落纸」是两个动作，同时发生会互相盖住 |

几条规矩：

- **只动 `opacity` / `transform`。** 布局一动，界面就像在跳，那正好和仪式相反。
- **开议的幕不吃操作**（`pointer-events: none`），也不拖慢任何东西：它盖住的是
  已经在跑的议事厅，不是等待中的空屏。
- **减少动效时四拍全退。** 样式那边靠全局规则把时长压到 0；开议这块幕是 JS
  定时器撑住的，不受时长规则管，所以它在挂载前自己问一次
  `prefers-reduced-motion` —— 否则降级之后会剩一块静止 1.2 秒的板子，比没有仪式更糟。
- 报告那 420ms 的延迟只为了让收尾条落定，不为别的；它不会让报告晚到，因为
  报告已经落盘了。

自测：`npm run test:css-dead-rules`（新增类名都要有消费者）、`test:contrast`。

## 外观媒体：内置预设 + 用户自己的开场与背景

设置 → 外观 里可以给应用换两样东西：**启动动画**与**主背景**。每样都有两条来源，
并列而不是互相替代：

| 来源 | 是什么 | 存在哪 |
| --- | --- | --- |
| 内置预设 | 随程序分发的那一份，点一下就套用、随时切回来 | `resources/media/`（打包后在 `resources/media`，不进 asar） |
| 用户上传 | 自己挑的文件，收进数据目录 | `userData/torra/media/` |

两者都接受 GIF / WebP / PNG / JPEG / AVIF 与 MP4 / M4V / WebM，选择即刻生效、下次启动保持。
偏好里记的是「用哪一份」（预设记 id、上传记文件名），不复制预设 —— 复制会留下一份
永不更新的副本，程序换了预设文件之后用户看到的还是旧的那一支。

| | 看见什么 | 边界 |
| --- | --- | --- |
| 启动动画 | 每次启动放一遍，居中、可点可 Esc 跳过 | 视频播完即收，最长 8 秒；动图固定停留 2.6 秒 |
| 主背景 | 铺在整个壳底下的图或视频，正文列（`.center-main`）自带一层玻璃底压在上面 | 视频窗口最小化时暂停；遮罩三档（淡 / 中 / 浓） |

几条规矩：

- **文件是复制进来的，不是记住路径。** 用户挑的是「桌面上的那个 mp4」；原文件会被
  移动、改名、丢进回收站，存一条绝对路径的话下次启动就是一块打不开的黑屏，而设置页
  还写着「已设置」。复制进 `userData/torra/media/` 之后，选择即刻成为应用的资产。
- **地址只走 `torra-media://`。** 渲染层是 sandbox + contextIsolation，CSP 只放行具名
  方案；`file://` 还会把 `C:\Users\…` 写进 DOM。文件名由主进程生成，路径穿越在方案层就断了。
- **扩展名要与内容对得上。** 选择时读文件头复核（PNG / JPEG / GIF / RIFF-WEBP / ftyp /
  EBML），对不上就当场拒 —— 一个改了扩展名的 mkv 在 `<video>` 里是静默失败，
  让用户以为「设了没反应」。图片上限 40 MB，视频 300 MB。
- **视频要 Range。** Chromium 的 `<video>` 用 206 分段读，不认「一次性 200 全量」；
  协议层自己切区间，300 MB 的片子不先进内存。
- **启动动画是遮罩，不是门。** 应用在它下面照常渲染与跑任务；系统要求减少动效时
  整块不挂 —— 一块静止的图挡在开场，比没有开场更糟。
- **背景层在壳内部的最底层。** `.app` 用 `isolation: isolate` 自成一个层叠上下文，
  背景层 `z-index: -1`：它在 `.app` 的底色之上、在所有正文之下。靠抬高 `.app`
  的 `z-index` 会把背景推到正文之上，标题栏先被一张图盖住。
- **开场带声，背景静音。** 开场那支片子只看一遍、看完就收，所以按文件本身的音轨播放
  （`autoplay-policy: no-user-gesture-required`，主进程模块顶层设）。背景则恒静音：
  它铺在整场会话底下、无限循环，一段循环的声音不是「背景」，是干扰。
  静音不是浏览器的硬性要求 —— 那条「无手势只能静音自动播放」的规矩属于普通网页，
  Torra 是用户自己装的桌面应用，开场是他自己挑的片子，掐成静音等于丢掉一半内容。
- **预设只读、上传可删，出厂默认就是预设。** 偏好里没有 `appearance` 这一段 = 从没设置过，
  回落到内置预设；有这一段（哪怕值是 `null`，即用户点过「移除」）就完全以用户为准 ——
  否则「移除背景」按下去，下次启动它又回来了。
- **正文列自己带玻璃底。** 之前只有议事厅的面片有底色，设置页 / 助手 / 工作台全透明；
  一旦设了主背景，那张图就直接穿到文字上，可读性靠遮罩浓度兜着，越淡越糊。
  `.center-main` 的 `--glass-bg` 把「背景是衬底、正文是前景」这条关系还回去：
  背景仍透过来，正文不再压在图上；没有背景时它与底色同源，看不出变化。

自测：`npm run test:appearance`（名字与内容两条口径、遮罩夹取、Range 三态、路径穿越、
预设白名单与槽位错配）。

## 任务台：把「一个会话」降级成实现细节

编码工作台以前一次只能伺候一个会话。几块活就得自己来回切，而人能同时盯的会话数是有上限的
（经验值三到五个）—— 瓶颈不在模型，在人。任务台把这条线跨过去：人只跟一个常驻的 Router
说话，它把这件事拆成几块互不干扰的活，派给下面的 Worker。

**Router 不动手。** 它手里只有分派与回收：`spawn_task` / `list_tasks` / `task_output` /
`intervene` / `cancel_task` / `finish`，没有编辑文件、跑命令的工具。否则「并行推进几个任务」
会退化成「一个人在几个会话里来回切」，加出来的架构一个字节都没省。

**每个任务一个 Worker。** 一个 Worker 一份 `AcpService` 实例：独立的进程、独立的授权、
独立的事件流。一个在等用户点头不会挡住另一个，一个崩了也不带走别的。任务板按阶段分组，
组标题的条数就是列表的条数 —— 不猜、不缩写。

**工具结果不进对话。** 人看到的是 Router 转述的一句；要看 Worker 的原文，就去点那一块活，
详情里是它的目标、目录、动作轨迹与输出尾巴。尾巴只留最后几千字：界面要的是「它现在说到哪儿」，
不是把整场正文搬进来。

**等授权时要说清楚它在问什么。** 任务卡上写一句「edit · 删掉 src/legacy」，详情里给「允许 / 拒绝」。
允许按它自己给的第一个选项回，拒绝回「不选」—— 选项名不能自己编。回错号等于替另一个请求拍板，
所以只收「正挂着的那一个、而且就是这一个号」。

**没配路由模型就直接说清该配哪个**，不猜一个模型上去，也不拿空串去撞端点。目录默认与编码工作台
同一份口径（最近用过的那个，没有就落到 `<userData>/acp-workspace`）：两个默认值就等于同一份代码
在两个目录下各改一遍。

**停得下来。** 两处都能停：任务卡上的「取消」，和 Router 忙时送出键变成的「停下」。任务取消
按进程树收（Windows 上 `shell: true` 起的是 `cmd.exe` 壳，agent 是孙进程，只杀壳它会被重挂到
别处继续跑）；已经收摊的阶段不再受理迟到的活事件，否则 `cancelled` 会被改回 `working`。
Router 叫停断掉正在等的那条连接，已声明的工具调用补一条「没执行」的回音 —— 少一条回音，
下一次请求就是 400。

自测：`npm run test:superagent` 三十七条 —— 任务状态机、三种 wire 的流式解析、工具清单与
execute 分支的对应。其中 Anthropic 的 `content_block_*` 分片与 OpenAI 流式工具调用的入参拼接
都是当年「模型一个字都没说」的形态，而且都不报错。

## 附录：这一层的红线

- **不提供任何规避验证码或风控的手段。** agent 那边遇到人机验证，Torra 停下来，
  让人当场手动接管。
- **凭据只存本机钥匙串或独立分区，不上传。** 适配器读的是用户自己机器上的登录态，
  Torra 不经手。
- **免掉全部授权的档位不开放**，主进程拒发、界面不画，两处都挡。
- **不替用户回答授权请求。** agent 要授权，选项照它给的列出来，决定权在人手里。

## 1. 背景与问题

重度 AI 用户在研究复杂问题时，需要同时询问多个在线 LLM（ChatGPT、Claude、Gemini、Kimi、DeepSeek 等）以获得全面答案。当前痛点：

1. **反复切换**：在 3~5 个网页间来回切换，打断心流；
2. **人工搬运**：手动复制粘贴 A 的观点给 B，用户扮演"传声筒"；
3. **信息过载**：N 个模型产出 N 份完整回答，用户自己提炼共识与分歧；
4. **无法收敛**：模型之间无法直接对话、互相质疑，讨论深度受限于用户转述能力。

### 1.1 现有方案的局限

| 方案 | 能解决 | 仍留下的问题 |
| --- | --- | --- |
| 手动多标签页 | —— | 全部痛点 |
| 多模型并答聚合（ChatALL / ChatHub 类） | 痛点 1、3 | 没有交锋，没有收敛；模型各说各话，结论仍靠用户自己拼 |
| 结构化多方对话（Consensus 类开源项目） | 痛点 4 | 需用户自备全部 API 额度；无网页版通道，用户已有订阅闲置 |

**Torra 的空位**：既要保留用户已有的网页版订阅（零额外成本），又要让模型真正互相听见对方说了什么。

## 2. 产品定位

> 一个多模型 AI 议事厅桌面客户端：用户提出议题，多个 LLM（网页版或 API）自动进行结构化讨论，逐步收敛分歧，最终输出一份带共识、分歧与溯源的报告。

一句话价值：把"用户当传声筒"变成"模型开圆桌会"。

### 2.1 目标

- 用户获取多模型共识的时间从 30~60 分钟缩短到 5 分钟以内；
- 报告可溯源：每条结论标注来源模型与轮次；
- 讨论过程完全透明、可随时介入与接管。

> **可行性校准**：5 分钟目标成立的前提是「轮内并行、轮间串行」的批次模型（见 6.2）。在默认配置（5 模型 × 3 轮）下，总计约 6 个串行批次，按单批 30~60 秒估算为 3~6 分钟，与目标吻合。若改为全串行（15 次顺序发言），实际需 8~15 分钟，**目标不成立**。因此并发模型是本产品的时间承诺前提，而非实现细节。

### 2.2 非目标（本期不做）

- 不做通用单模型聊天助手；
- 不做模型能力排行榜（避免立场争议）；
- 不做移动端；
- 不做团队协作（远期 P2）；
- **不托管用户 API Key**（Key 仅存本机系统钥匙串）；
- **不提供任何规避风控/验证码的手段**（详见 11.3 合规红线）。

## 3. 目标用户与场景

| 用户 | 场景 | 核心诉求 |
| --- | --- | --- |
| 研究员 / 分析师 | 技术路线可行性论证，需要多方推演 | 穷尽反对意见，识别盲区 |
| 产品经理 / 创业者 | 功能取舍决策前的多视角辩论 | 快速拿到决策依据与风险清单 |
| 内容创作者 | 选题论证、观点碰撞找角度 | 观点素材与对立面 |
| 深度学习者 | 复杂概念的多模型解释对比 | 同一概念的多种解释路径 |
| 企业用户 | 方案评审前的多智能体预审 | 保留分歧、责任可追溯 |

### 3.1 首要用户与使用频次假设

MVP 阶段首要用户为**技术决策者与研究者**（上表前两行），典型使用频次为每周 2~5 次单场讨论。理由：该群体已有多个模型订阅（网页版或 API），付费意愿与迁移成本敏感性都最低，且对"保留分歧"的价值有明确认知——普通用户更想要一个答案，而本产品给的是一份带保留意见的报告。

> 这一取舍意味着：**MVP 不追求用户规模，追求单场讨论的质量闭环。**

## 4. 产品形态决策：为什么是桌面客户端

| 形态 | 评估 | 结论 |
| --- | --- | --- |
| 独立 Web 应用 | 无法持有网页版登录态 | 放弃 |
| 浏览器插件 | 跨标签页自动化受限、风控高 | 远期可选 |
| **桌面客户端** | 可常驻后台 WebView 池、持久化 cookie 分区、完整自动化能力、可离线存储 | ✅ 采用 |

核心机制：**用户看到的是一个页面，后台常驻一群页面**。

### 4.1 形态带来的三项结构性优势

1. **登录态所有权**：cookie 分区持久化在本地，不经过任何中间服务器；
2. **零 Web 服务器成本**：核心编排全在主进程，Torra 不运营推理服务，只在用户主动分享时涉及云存储；
3. **可离线**：SQLite 本地库 + 本地 PDF 导出，断网可用（仅 API 通道与分享功能依赖网络）。

### 4.2 形态带来的三项结构性代价（必须正视）

| 代价 | 影响 | 缓解 |
| --- | --- | --- |
| 站点改版即适配器失效 | 维护成本随接入站点数线性增长 | 声明式适配器 + 热更新 + 健康自检（见 6.4、14） |
| 网页自动化存在账号风险 | 用户可能触发平台风控 | API 优先默认、拟人化、频率上限、不绕验证码、风险明示（见 11.3） |
| WebView 资源占用 | 多实例常驻内存高 | 后台节流 + LRU 挂起 + 内存回收（见 6.2、11.1） |

> 这三项代价是选择桌面端形态的必然结果，不是可以"优化掉"的 bug。评审时应把它们视为**一期的设计输入**而非二期改进项。

## 5. 核心概念定义

| 概念 | 定义 |
| --- | --- |
| 议题（Topic） | 用户输入的讨论主题 + 背景材料（可选附件/链接） |
| 讨论（Session） | 一次多模型议事过程，由若干轮次组成 |
| 轮次（Round） | 一轮中每个参与模型依次发言一次 |
| 批次（Batch） | 轮内并行的一组发言调用；一轮 = 1 个发言批次 + 1 次主持小结 |
| 主持智能体（Moderator） | 控制流程：总结上轮、指定发言、判断收敛。**默认不参与发言**（见 6.5） |
| 传输方式 | WebviewTransport（驱动后台网页）/ ApiTransport（官方 API 直连） |
| 共识度（Consensus Score） | 每轮由主持模型按可计算维度评估的一致程度（0–100%） |
| 收敛（Convergence） | 共识度达阈值（默认 85%）或达到最大轮次时触发 |
| 未决分歧（Open Dispute） | 经两轮以上仍未消解的议题点，强制保留至报告，不允许被摘要抹平 |
| 报告（Report） | 结构化产出：共识、分歧、论据、溯源 |

## 6. 系统架构

### 6.1 总体架构

```javascript
┌────────────────────────────────────────────┐
│ 渲染层：React 主界面（议事厅 / 转播 / 接管）   │
│ 左模型栏 ｜ 中讨论流 ｜ 右共识面板            │
└──────────────────┬─────────────────────────┘
                   │  SSE 事件流
┌──────────────────▼─────────────────────────┐
│ 主进程：编排引擎（状态机）                    │
│ 轮次控制 · 上下文裁剪 · 共识评估 · 消息路由    │
│ 统一 Agent 接口：send(prompt) → stream(text) │
└──────┬───────────────────────┬─────────────┘
       │                       │
┌──────▼─────────┐   ┌─────────▼────────────┐
│ Webview 池      │   │ API 传输层            │
│ 每个网页版 LLM  │   │ OpenAI 兼容协议优先    │
│ 一个隐藏实例     │   │ 每厂商一个适配器        │
│ 独立 cookie 分区 │   └──────────────────────┘
│ 站点适配器注入    │
└────────────────┘
```

### 6.2 轮次调度模型（时间承诺的实现基础）

**轮内并行、轮间串行。** 每一轮由两个串行批次组成：

```
Round N:
  ┌─ Batch A（并行）───────────────────────────────────┐
  │ 参与模型 1..N 同时发起发言                         │
  │ 每个模型看到的输入 = 同一份「上一轮结束时的快照」   │
  │ → 轮内模型互相看不到本轮他人发言（保证独立性）      │
  │ → 全部完成 / 失败降级后，进入 Batch B              │
  └───────────────────────────────────────────────────┘
                     ↓
  ┌─ Batch B（串行，1 次调用）────────────────────────┐
  │ 主持模型：摘要 + 分歧登记 + 共识打分 + 指定下轮顺序  │
  └───────────────────────────────────────────────────┘
                     ↓
              收敛判定 → 未达阈值且轮次未满 → Round N+1
```

**时序预算（默认 5 模型 × 3 轮）**

| 批次 | 数量 | 单批预估 | 小计 |
| --- | --- | --- | --- |
| 发言批次 | 3 | 30~60s | 1.5~3 min |
| 主持小结 | 3 | 10~20s | 0.5~1 min |
| **合计** | **6** | — | **2~4 min** |

> 若某个参与模型走 webview 通道且站点响应慢，单批耗时由**最慢的那个模型**决定，而非平均。这是并行的固有代价：慢通道拖累整批。缓解手段见 6.2「通道降级」。

**通道降级规则（超时保护）**

| 情况 | 处理 |
| --- | --- |
| 单模型超过 `max_wait_s`（默认 120s）未返回 | 标记该模型本轮缺席，不阻塞整批；发言位显示缺席占位 |
| 同一模型连续 2 轮缺席 | 自动切换到其备用通道（API 优先）；无备用通道则移出本场讨论并在报告标注 |
| 发言批次整体耗时 > 180s | 提示用户可切换"仅 API 模型"继续 |

**主持模型失效处理（致命故障，必须有降级）**

主持模型是小结与收敛判定的唯一执行者，其失效不可容忍：

1. 首次失败 → 自动重试 1 次（换备用通道）；
2. 仍失败 → **暂停讨论**，弹出决策弹窗：更换主持模型 / 切换为"无主持降级模式"；
3. 无主持降级模式：取消自动收敛判定，改为跑满最大轮次后直接出报告，报告标注"本场无主持评估，共识度不可用，分歧未做结构化消解"。

### 6.3 后台 WebView 池（核心机制）

- 每个网页版模型在后台常驻一个不可见 WebContents（Electron `WebContentsView`，`autoHideMenuBar`，不 attach 到窗口或隐藏于主窗口之下）；
- 各实例使用独立 `session.partition` 持久化登录态（cookie 有效期内永久待命）；
- 启动客户端时按分区恢复会话，状态灯自动更新；
- 资源控制：未参与讨论的 WebView 可 `webContents.setBackgroundThrottling(true)` 并挂起渲染，仅活跃实例全速运行；内存超过阈值时 LRU 回收非活跃实例（登录态不丢，重新激活即可）。

> **实现提示**：`session.partition` 的持久化在 Electron 中默认不落盘，需通过 `session.fromPartition(name, { persist: true })` 显式开启，否则重启后所有登录态丢失。这是本模块最易踩的坑。
>
> **落地注意**：判定"生成完成"不建议依赖 CSS 伪类 `:hidden`（WebContentsView 内的样式计算时序不稳定），改用 JS 侧轮询 `stopButton.offsetParent === null` 或 MutationObserver 监听停止按钮的显隐变化，更可靠。

### 6.4 统一 Agent 抽象

所有模型实现同一接口，编排引擎不感知传输方式：

```javascript
interface Agent {
  id: string              // 模型标识
  transport: 'webview' | 'api'
  status: 'ready' | 'busy' | 'expired' | 'adapter-broken' | 'disabled'
  send(context: TurnContext): AsyncIterable<string>   // 流式输出
  healthCheck(): Promise<boolean>
  takeover(on: boolean): void   // 手动接管/交还（仅 webview）
}
```

- 讨论中可随时把某模型从 webview 切换到 API（或反向），不中断会话；
- **API 优先原则**：用户同时配置了某模型的 Key 和网页登录时，默认走 API，网页作为备用通道。

> **混合通道的一致性说明**：同一场讨论中允许部分模型走 API、部分走 webview。两条通道的模型看到的是**完全相同的上下文快照**，因此讨论质量不受影响。但需注意两点：(1) 延迟差异大，webview 模型常成为整批的短板；(2) 部分 webview 站点的模型可能带有站点侧的功能差异（如联网搜索、文件解析），需在模型选择器上标注能力差异，避免用户误判。

### 6.5 主持模型规则

**主持模型默认从参与模型中排除。** 若让主持同时作为发言选手，会产生裁判兼运动员的结构性偏误——它在小结时天然更容易把自己的路径描述为共识。

| 规则 | 说明 |
| --- | --- |
| 默认行为 | 主持模型不参与本场发言，不计入共识统计与共识度计算 |
| 用户指定兼任 | 允许兼任，但弹出明确警示："主持模型同时发言可能高估共识，建议分开指定" |
| 主持能力要求 | 需支持结构化 JSON 输出；不支持者不能担任（设置页标注"不支持主持"） |
| 主持可换 | 讨论中可更换主持模型，从下一批次生效 |

### 6.6 站点适配器规范

每个站点一个声明式适配器（YAML），与主程序分离、支持热更新：

```yaml
id: chatgpt
name: ChatGPT
transport: webview
entry: https://chatgpt.com/
selectors:
  input: div[contenteditable="true"][role="textbox"][aria-label*="ChatGPT" i], textarea[placeholder*="ChatGPT" i], textarea#mobile-composer-prompt, #prompt-textarea
  send: button[aria-label*="Send message" i], button[aria-label*="发送消息"], button[data-testid=send-button]
  stream: div[data-message-author-role=assistant] [data-testid=conversation-turn]:last-child .markdown
  stop: button[aria-label*="Stop" i], button[aria-label*="停止"], button[data-testid=stop-button]
completion:
  mode: stop_button_hidden   # 停止按钮消失 = 生成结束
  timeout_s: 120
automation:
  typing_delay_ms: [80, 220]     # 拟人化键入
  pre_send_pause_ms: [500, 1500]
  max_wait_s: 120
  jitter: true                  # 每次调用的时间抖动开关
health_probe: div[contenteditable="true"][role="textbox"][aria-label*="ChatGPT" i], textarea[placeholder*="ChatGPT" i], textarea#mobile-composer-prompt, #prompt-textarea
verified_at: 2026-10-01
```

适配器带每日健康自检（探测选择器是否存活），失效时标记 `adapter-broken`。

> `verified_at` 供客户端展示"上次验证时间"，让用户判断适配器新鲜度。热更新推送时若某适配器距上次成功验证超过 30 天，客户端应提示"长期未验证，可能已失效"。

### 6.7 编排引擎状态机

```javascript
INIT → LOGIN_CHECK → READY → ROUND_START
  → AGENT_BATCH(并行×N) → MODERATOR_SUMMARY → CONSENSUS_EVAL
  → ── score≥阈值 ──→ REPORT_GEN → DONE
  → ── score<阈值 且 轮次未满 ──→ ROUND_START
  → ── 轮次已满 ──→ REPORT_GEN(含保留分歧)
任意状态 ← 用户插话 / 终止 / 接管 / 切换通道
MODERATOR_SUMMARY ← 失败 → MODERATOR_RETRY → 失败 → PAUSE_FOR_USER
```

- 每轮发言模型可见：议题 + 背景材料 + 全部历史（超长历史由主持模型摘要压缩后注入）；
- 支持点名：主持模型可要求模型 X 针对性回应模型 Y 的某观点；
- 共识评估：主持模型结构化输出 JSON，程序只解析展示。

**共识度评分的可计算定义**

主持模型不得只给一个主观总分。必须按三维度分别给分并附依据，程序校验后才接受：

| 维度 | 含义 | 校验规则 |
| --- | --- | --- |
| 立场一致度 | 各模型在已识别议题点上的立场是否一致 | 可由程序从参会模型发言的立场标记直接核算 |
| 论点重合度 | 各模型论证路径的交集大小 | 要求主持列出至少 2 条被多数模型共同提及的论点 |
| 分歧收敛趋势 | 未决分歧数量相对上轮的变化 | 程序自动计算，主持仅确认不修改 |

`score = 0.4×立场一致度 + 0.3×论点重合度 + 0.3×收敛趋势`

> **程序校验规则**：若主持输出的 JSON 缺少任一维度的依据，或声明的共识点无任何模型发言支持（`support` 字段指向不存在的发言 ID），**拒绝该次小结并要求重打**。这条规则是"假收敛"的主要防线——主持模型可能倾向于宣布一个不存在的共识，程序的机械校验比模型的自我约束更可靠。

### 6.8 上下文管理策略

**结构化纪要优先于自由文本摘要。** 讨论历史注入模型时不是拼接全文，而是注入如下结构：

```javascript
interface Digest {
  confirmed: ConsensusPoint[]      // 已确认共识（含支持方列表）
  open: OpenDispute[]             // 未决分歧（含双方论据摘要）—— 逐字保留，不允许概括
  explored: string[]              // 已被充分讨论并排除的方向
  rounds: RoundMeta[]             // 轮次元信息（发言模型、时间、token）
}
```

**压缩触发与保分歧规则**

| 条件 | 动作 |
| --- | --- |
| 累计历史 token < 8k | 不压缩，全文注入 |
| 累计 8k~20k | 主持模型生成滚动摘要，`confirmed` 与 `explored` 可概括 |
| 累计 > 20k 或接近模型上下文上限 | 强制压缩：滚动摘要 + **未决分歧清单逐字保留** |

> **保分歧是硬约束。** 主持模型在压缩时天然倾向"总结出重点"，而未决分歧恰恰不是"重点"。若不强制保留，跨轮次后早期分歧会静默消失，用户看到的是一份虚假的和谐报告。因此 `open` 字段在整个会话生命周期内只增不减（除非某条分歧被明确消解并记录消解依据），且压缩时逐字搬运、不经改写。

## 7. 功能需求

### 7.1 P0（MVP 必须有）

| 编号 | 功能 | 说明 |
| --- | --- | --- |
| P0-1 | 登录引导 | 首次添加网页版模型：弹出真实窗口完成登录；会话存入独立分区；状态灯绿=有效 / 红=过期 |
| P0-2 | API Key 管理 | 本地加密存储（系统钥匙串）；API 模型即配即用；用量与费用统计；**单场预算上限，达到上限自动收束并出报告（标注"预算受限"）** |
| P0-3 | 议题发起 | 输入议题 + 附件（PDF/链接）；选参与模型、主持模型、策略（圆桌/辩论/评审）、最大轮次（默认 3）、共识阈值（默认 85%）、预算上限 |
| P0-4 | 多方讨论引擎 | 轮内并行批次推进、流式输出、点名回应、上下文结构化纪要注入 |
| P0-5 | 三种呈现模式 | 议事厅（默认）/ 转播（点击头像看后台页面实况）/ 接管（手动操作，可交还） |
| P0-6 | 共识面板 | 共识度实时曲线（三维度分解展示）+ 共识点/分歧点清单（形成中/已共识/保留分歧）+ 费用统计与预算余量 |
| P0-7 | 报告生成与导出 | 执行摘要 / 共识（标注认同模型与轮次）/ 分歧双方论据 / 盲区 / 溯源链；导出 Markdown、PDF（均为本地文件） |
| P0-8 | 用户介入 | 讨论中随时插话（全员或指定模型）、一键终止并出报告 |
| P0-9 | 状态与降级 | 会话过期→提示重新登录；适配器失效→标记并支持手动接管；单模型故障不中断整体讨论，报告标注缺席；**主持失效→暂停并提供换主持/无主持降级两条出路** |

> **P0-7 的范围修正**：初稿把"只读分享链接"列入 P0，但分享链接需要服务端托管，与"非目标：数据本地存储"及"Key 不托管"存在架构冲突。**MVP 阶段只做本地导出（Markdown / PDF），云端只读分享移至 P1**，且必须由用户显式选择上传（数据外传二次确认 + 可随时撤销）。Pro 的云端能力不作为 MVP 前提。

### 7.2 P1（快速跟进）

- 报告局部追问（针对某条结论展开再讨论）；
- 角色设定（自定义各模型人格/立场，如"指定怀疑论者"）；
- 历史会话列表、搜索、fork 继续讨论；
- 议题模板市场（技术选型/商业决策/论文评审）；
- 云端只读分享链接（用户显式上传、可撤销）。

### 7.3 P2（远期）

- 定时议题（每周固定时间自动讨论）；
- 团队空间（多人围观、各自 @模型）；
- 本地模型接入（Ollama，走 ApiTransport）；
- 浏览器插件形态（复用 Torra 的适配器规范与编排逻辑）。

### 7.4 策略模式说明

| 模式 | 行为 | 适用 |
| --- | --- | --- |
| 圆桌 | 所有模型平行发言，无强制反驳 | 广度探索、选题发散 |
| 辩论 | 主持指定正反双方，强制点名回应 | 决策取舍、需要对抗性意见 |
| 评审 | 主持扮演评审角色，按预设维度逐项打分 | 方案评审、论文互评 |

> 策略仅改变主持 Prompt 中的角色定义与发言顺序安排，不改变底层调度模型。MVP 阶段三者共用同一套编排，仅 Prompt 模板不同——避免为策略差异引入额外架构复杂度。

## 8. 交互设计

### 8.1 主界面布局（1280×800 基准，三区可调）

```javascript
┌──────────────────────────────────────────────────────┐
│ 标题栏：议题名 · 轮次指示 R2/3 · 状态汇总 · 终止按钮     │
├──────┬──────────────────────────────┬────────────────┤
│ 模型栏│        议事厅（讨论流）        │  共识面板 220px │
│ 64px │  或：转播画面（嵌入 WebView）   │  共识度曲线     │
│ 头像+│                              │  三维度分解     │
│ 状态灯│                              │  共识/分歧清单  │
│      │                              │  费用/预算     │
├──────┴──────────────────────────────┴────────────────┤
│ 插话输入框（常驻）：对全员或 @指定模型发言               │
└──────────────────────────────────────────────────────┘
```

> 布局为 1280×800 基准，实际实现需保证 1024×768 仍可用：模型栏收窄为头像单列，共识面板可折叠为图标条。

### 8.2 三种模式切换逻辑

- **议事厅**：默认。统一讨论流；消息带彩色模型标识 + 轮次标签；引用他人观点时高亮被引用内容；主持小结用左侧粗竖线区分；
- **转播**：点击左栏模型头像 → 该 WebView 以画中画嵌入中央区，实时显示自动键入/发送/流式回复全过程；仅 webview 型模型可用；
- **接管**：转播画面内切换；用户可直接操作真实页面（处理验证码、纠偏、重新登录）；「交还自动」恢复自动化。会话过期时按钮变为「重新登录」。

> **转播模式的双面性（需在设计中正面处理）**：转播让用户看见"机器人正在用我的账号操作"，这对建立信任极有价值——用户能立刻发现"这个站点适配器选错了元素""这个模型跑题了"。但它同时把后台动作完全暴露给用户，也意味着用户能看见自己的账号在被自动操作。因此转播画面必须常驻一个状态标识（"Torra 正在自动操作此页面"），避免用户在不自知的情况下被风控，也避免用户误以为是自己操作。

### 8.3 关键交互细节

- 新发言打字机式流式出现；
- 同一批次内的发言**按完成顺序追加**而非按模型固定顺序（因为并行执行），并在该批次头部标注"本轮 N 个模型并行发言"；
- 共识面板"形成中"条目红点脉动，提示讨论正围绕它进行；
- 缺席发言以虚线占位卡片显示：「{模型名} 本轮未响应 · 查看原因」，不静默消失；
- 用户插话后，下一批次由主持模型将插话内容分发给相关模型；
- 深色模式优先；三区宽度可拖拽调节；窗口尺寸记忆。

### 8.4 空状态与异常态

| 状态 | 表现 |
| --- | --- |
| 首次启动 | 风险确认墙（见 11.3）+ 引导页：选择添加网页登录或 API Key |
| 未添加任何模型 | 引导页：站点登录指引 + API 配置指引 + 各平台入口链接 |
| 会话过期 | 红灯 + 转播画面内一键重新登录 |
| 适配器失效 | 发言位降级提示，其余模型继续，报告标注缺席；提供"提交适配器修复"入口 |
| 主持模型失效 | 暂停讨论 + 弹窗：更换主持 / 无主持降级模式（说明其代价） |
| 共识度连续 2 轮不升 | 弹条提示用户介入或调整策略（加赛一轮 / 提高阈值 / 收束出报告） |
| 预算接近上限 | 进度条转黄 + 提示"是否提前收束" |
| 全部通道不可用 | 错误页 + 诊断信息导出（不含任何凭据与聊天内容） |

## 9. 视觉规范

- **学术记事本气质**：黑白灰为主，每模型仅一个标识色（蓝/红/绿/紫/灰），其余界面零彩色；
- 共识度曲线黑色主线；已共识绿点、分歧红点；曲线下方以浅色带区显示三维度分解；
- 细边框（1px）、圆角 10~12px、无阴影无渐变；
- 字体：UI 无衬线；报告正文衬线提升正式感；
- 深色模式为默认主题。

> **色彩使用纪律**：模型标识色与语义色（共识绿 / 分歧红）**不得混用**。否则"红色的分歧"会被误读为"红色的那个模型的观点"。模型色只出现在头像环、发言卡左侧色条、@提及中；语义色只出现在共识面板与报告中。

## 10. 技术方案

| 模块 | 方案 |
| --- | --- |
| 壳 | Electron 33+，主进程 Node 20 |
| 渲染层 | React 18 + Vite，Zustand 状态管理 |
| 进程隔离 | `contextIsolation: true` + `sandbox: true`；preload 通过 contextBridge 暴露白名单 API |
| 编排引擎 | 主进程状态机，事件驱动，SSE 推送到渲染层 |
| WebView 池 | `WebContentsView` + 独立 `session.partition`（须 `persist: true`），LRU 挂起 |
| 注入 | preload 脚本 + 适配器选择器；站点页面零 Node 权限 |
| API 层 | OpenAI 兼容协议优先，每厂商适配器独立队列限速 |
| 存储 | SQLite（会话/报告/纪要）+ 系统钥匙串（Key） |
| 上下文压缩 | 滚动摘要 + 未决分歧逐字保留（见 6.8），轻量模式可省 60%+ token |
| 拟人化 | 键入延迟、随机停顿、抖动开关（见适配器字段） |

## 11. 非功能需求

### 11.1 性能

| 指标 | 目标 |
| --- | --- |
| 议事厅首屏加载 | < 2s |
| 流式首字延迟 | < 3s（API 通道）/ < 8s（webview 通道） |
| 5 个后台 WebView 常驻内存 | < 1.5GB |
| 单模型缺席时整批阻塞 | 最多等待 `max_wait_s`（120s），超时即降级 |
| 100 场讨论后内存 | 无持续增长（LRU 回收有效） |

### 11.2 安全

- 渲染进程 `contextIsolation: true` + `sandbox: true`；
- 站点 WebView 页面零 Node 权限，仅通过 preload 暴露受控桥接方法；
- API Key 仅存系统钥匙串（macOS Keychain / Windows Credential Manager），**不落 SQLite、不进日志、不进诊断导出包**；
- 诊断导出包仅含：版本号、适配器 ID、状态码、错误堆栈，不含聊天内容与凭据；
- 分享链接上传前二次确认，明确提示"报告将离开本机"。

### 11.3 合规红线

> **这是桌面 + 网页自动化形态的生存前提，须作为一期的强约束而非合规补丁。**

| 红线 | 规则 |
| --- | --- |
| 风险明示 | 首次启动展示风险确认墙，明示"网页自动化可能触发平台风控甚至封号，风险由用户自行承担"；设置页常驻入口查看 |
| 不绕验证码 | 出现验证码/人机验证时**停止自动化并引导用户手动接管**，严禁任何自动破解尝试 |
| 不伪造身份 | 不注入脚本隐藏自动化特征、不篡改页面指纹 |
| 频率上限 | 单会话发言频率上限 + 每日总轮次上限，均可配置，默认值取保守档 |
| 拟人化仅用于降低误伤 | 键入延迟等参数用于避免"机器瞬间发出上百次请求"的异常模式，**不用于伪装人类身份欺诈** |
| 站点 ToS 尊重 | 首次接入某站点时提示其服务条款可能限制自动化，由用户确认后继续 |
| 数据外传显式化 | 任何离开本机的数据（分享链接）必须由用户主动触发并可撤销 |

> 商业化前需法务确认：Torra 的自动化行为在各目标站点的服务条款下的定性。**这一项列为 M4 商业化的前置条件，不解决则不做 Pro 的网页版通道变现。**

## 12. 成功指标（上线 3 个月）

| 指标 | 目标 | 统计口径 |
| --- | --- | --- |
| 首次议题 → 拿到报告完成率 | ≥ 70% | 发起后 30 分钟内产出报告且用户未在报告页停留超过 60 秒即视为"未完成"（防止导出后立刻弃用） |
| 单议题平均耗时 | ≤ 5 分钟 | 从点击开始到报告生成完毕的墙钟时间，剔除用户人工介入时间 |
| 报告导出/分享率 | ≥ 40% | 报告生成后 7 日内至少一次 Markdown/PDF 导出或分享 |
| 周留存 | ≥ 30% | 自然周内发起 ≥ 2 次议题的用户数 / 当周有活跃的用户数 |
| 适配器可用率 | ≥ 90% | 参与讨论的 webview 模型未因适配器失效而缺席的场次占比 |

> **补充反向指标**（防止指标被规避）：报告页"未决分歧"区域的平均条目数需 ≥ 1。若长期为 0，说明产品退化成了"表面附和的共识机"，与 Torra 的核心价值主张相悖，需在迭代中修正提示词与评分机制。

## 14. 风险与对策

| 风险 | 影响 | 对策 |
| --- | --- | --- |

| 慢通道拖累整批 | 中 | 单模型超时降级 + 超 180s 提示切换纯 API 模式 |
| 单站点依赖 | 低 | 适配器热更新可先于客户端发版送达用户 |

| 方案 | 通道 | 是否真正交锋 | 收敛与分歧结构化 | Torra 的差异 |

## 16. 附录

### 附录 A：主持模型编排 Prompt 框架

```javascript
你是本场多模型讨论的主持人。议题：{topic}；背景材料：{materials}
参与模型：{agents}。当前第 {round}/{max_round} 轮。

你的任务（每轮结束执行）：
1. 阅读本轮所有发言，输出结构化 JSON：
   { consensus_points: [{claim, support: [agent_ids], confidence, evidence_ref}],
     open_disputes: [{claim, sides: [{agent_id, argument}]}],
     score_dimensions: { agreement, overlap, trend },
     score: 0-100,
     next_round_order: [agent_ids],
     callout: { target_agent, quote_from_agent, instruction } | null }
2. 如需某模型回应另一模型，用 callout 字段说明。

评分规则：
- agreement（立场一致度）：各模型在已识别议题点上的立场是否一致
- overlap（论点重合度）：被 ≥2 个模型共同提及的论点，需列出具体条目
- trend（收敛趋势）：未决分歧数量相对上轮的变化
- score 反映核心问题上的实际一致程度，表面附和不得加分

硬约束：
- 每条 consensus_point 的 support 必须指向真实存在的 agent_id 与发言，
  不得凭空生成共识；
- 不得为了推进收敛而合并本质不同的观点；若分歧无法消解，
  保留在 open_disputes 中。
```

> 附录 A 相比初稿新增了 `evidence_ref`（共识点必须指向具体发言）、`score_dimensions`（三维度分项）、`next_round_order`（主持显式指定顺序），并在硬约束中明确"不得凭空生成共识"——这三条与 6.7 的程序校验形成双保险：程序负责机械校验，Prompt 负责引导主持自报。

### 附录 B：参会模型发言 Prompt 框架

```javascript
议题：{topic}
讨论记录（或结构化纪要）：{digest}
{若有 callout}：主持人要求你针对性回应 {target_agent} 的观点："{quote}"
请输出你的立场与论据（≤{max_len} 字）。引用他人观点时标注来源轮次。

{若 digest.open 非空}：当前仍存未决分歧：{open_list}。
        若你能消解其中某项，请直接论证；不能则明确指出分歧为何仍在。
```

> 相比初稿新增最后一段：把未决分歧显式告知参会模型，否则模型不知道自己"该反驳什么"，只能重复已有观点——这是"假收敛"在发言侧的诱因。

### 附录 C：报告生成 Prompt 框架

```javascript
基于完整讨论记录生成共识报告，结构：
1. 执行摘要（≤200 字）
2. 共识结论：每条标注认同模型数与来源轮次，附关键论据
3. 保留分歧：双方论据摘要（各 ≤100 字）+ 为何未能消解
4. 未覆盖风险/盲区（主持人补充）
输出 Markdown，所有结论须可在讨论记录中找到出处。
禁止：删除未决分歧以使报告显得一致；把"无人反对"表述为"一致认同"。
```

> 相比初稿新增禁止条款。报告是用户最终交付物，也是"假收敛"的最后一道出口——如果报告层面把分歧抹掉，前面的机制全部失效。
